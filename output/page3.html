Our updater is the download page, and the one string that stops a reinstall wiping your licence is productName

📅 Nov 01, 2026  |  Category: Technology  |  Read Source →

Notifio is an Electron app that watches rental search pages and alerts you when a new listing appears. It ships as a 600MB DMG or a 300MB Windows installer, and it has no auto-updater at all.

That is written down, in app/RELEASES.md, as a three-step procedure:

There is no auto-update. To ship a new version:

  1. Bump version in app/package.json.
  2. Build and upload the installers exactly as above (overwriting the files in R2).
  3. Tell users to download and install again from the download page.

Grep the app for autoUpdater or electron-updater and you get nothing. There is no publish block in the electron-builder config either, which means no latest.yml and no latest-mac.yml are generated, so there is nothing an updater could read even if one were added tomorrow.

I think this is the right call for this product and I want to lay out what it actually costs, because "just tell people to reinstall" is a sentence that quietly depends on a lot of things being true.

Why there is nothing to update against

The installers are large because each one carries a browser. The breakdown in our own release notes is roughly 350MB of Electron, 180MB of Playwright's Chromium at a pinned revision, and 70MB of node modules and app code. Shipping a delta updater over that is real work, and the thing being updated changes a few times a year.

The second reason is that an auto-updater is a background process that downloads and swaps a 600MB application while the app is doing the one job it exists to do, which is being awake and watching. An update that interrupts monitoring for the fifteen minutes somebody's ideal flat was listed is worse than no update.

So: no updater, and the download page is the update channel.

The thing that makes a reinstall safe

Reinstalling only works because nothing the user owns is inside the app. Every writable path is resolved in one 56-line module:

export const USER_DATA_DIR = app.getPath('userData'); export const DATA_DIR = path.join(USER_DATA_DIR, 'data'); export const BROWSER_DATA_DIR = path.join(USER_DATA_DIR, 'browser-data'); export const CONFIG_PATH = path.join(USER_DATA_DIR, 'config.json'); export const PROFILE_PATH = path.join(USER_DATA_DIR, 'profile.json'); export const ENTITLEMENT_PATH = path.join(USER_DATA_DIR, 'entitlement.json'); export const RECIPES_PATH = path.join(USER_DATA_DIR, 'recipes.json'); export const LEDGER_DIR = path.join(USER_DATA_DIR, 'ledger'); export const FINDS_PATH = path.join(USER_DATA_DIR, 'finds.json');

Eight paths under one root, and the comment above them says why:

/** * Inside a packaged asar, __dirname is read-only. All writable data must live * in app.getPath('userData') which resolves to: * Windows: %APPDATA%\Notifio * macOS: ~/Library/Application Support/Notifio */

The licence is in config.json along with the saved searches. Drag a new build into /Applications, or let the NSIS installer replace the old one, and all of it is still there, so nobody re-activates and nobody re-enters their searches.

Now look at the last path component in those two example paths. Notifio is not a constant anywhere in the source. It is the productName field in the build config:

"build": { "appId": "app.notifio", "productName": "Notifio", ... }

Electron derives app.getPath('userData') from the application name, which for a packaged app is that string. Rename it to "Notifio Desktop" in a moment of tidying, ship the build, and every existing user launches an app that looks at %APPDATA%\Notifio Desktop, finds nothing, seeds a fresh config, and asks them to activate a licence they already own. Their old data is not gone, it is simply not where the new build looks, which is a worse failure than deleting it because nothing anywhere reports an error.

Our release notes carry the warning in bold, which is the right place for it and the wrong mechanism:

Keep productName as "Notifio" because it anchors the userData path. Renaming it would orphan every user's existing config and licence.

A warning in a markdown file is a comment with extra steps. The enforceable version is four lines in the release script, which already reads and rewrites package.json to bump the version: assert that build.productName is exactly Notifio and refuse to build if it is not. A release script that will not ship a rename is worth more than a sentence asking people not to do one.

The seed that never seeds

First run creates the directories and writes a default config:

export function initDataDirs(): void { fs.mkdirSync(DATA_DIR, { recursive: true }); fs.mkdirSync(BROWSER_DATA_DIR, { recursive: true }); fs.mkdirSync(LEDGER_DIR, { recursive: true }); if (!fs.existsSync(CONFIG_PATH)) { const bundledConfig = path.join(__dirname, '..', 'config.json'); if (fs.existsSync(bundledConfig)) { fs.copyFileSync(bundledConfig, CONFIG_PATH); } else { fs.writeFileSync(CONFIG_PATH, JSON.stringify(DEFAULT_CONFIG, null, 2), 'utf8'); } } }

The if (!fs.existsSync(CONFIG_PATH)) is the second half of what makes reinstalling safe: the seed is skipped when a config is already there, so an upgrade cannot overwrite somebody's searches with an empty list.

The branch above it, though, is dead. app/config.json does not exist in the repository. The electron-builder files array names it anyway, along with two directories that also do not exist:

"files": [ "dist-ts/**/*", "public/**/*", "assets/**/*", "config.json", "data", "browser-data", ... ], "asarUnpack": [ "node_modules/playwright/**/*", "playwright-browsers/**/*", "config.json", "data", "browser-data" ]

Three phantom entries in the packaging config, repeated across two lists, left over from when listing snapshots and the browser profile lived inside the app directory rather than in userData. They are harmless, electron-builder does not mind being told to include something that is not there, and they are exactly the kind of leftover that makes somebody later believe a shipped default config exists.

Two things follow from the branch being dead. Every fresh install gets DEFAULT_CONFIG, an empty email and an empty search list, which is the right onboarding anyway. And if we ever did want to ship a default search, adding config.json back would only reach new installs, because the seed is skipped for everyone who has already run the app once. A "default" in a desktop app means "default for people who have not used it yet", and that is worth being deliberate about rather than discovering.

What the user is not told

The update path works. The experience around it has four gaps, and three of them are the same gap.

Nothing tells you a new version exists. Not a banner, not a check, nothing. The user's cue that they should reinstall is an email, or this blog.

Nothing tells you which version you have. app.getVersion() does not appear in the codebase. The version in package.json is 1.1.0, the release script bumps it, uploads it as R2 object metadata, and exactly one script ever reads it back. The app never shows it. I ran into the other end of this gap today while writing about the price the app sends back to checkout: the server would like to behave differently for builds from before a feature existed, and it cannot, because no request from the app carries a version.

Nothing tells us which version you have either. The licence check runs against our server whenever its cached answer is more than six hours old, and that request is the obvious place for one more field. One string in that request would turn "are people still on the old build" into a query instead of a guess.

And on macOS, every reinstall is a Gatekeeper prompt. There is no signing identity and no notarisation step in the build config, so the DMGs are unsigned, which our own release notes acknowledge with a "right-click, Open" instruction. For an app whose entire pitch is that it runs quietly in the background, asking the user to defeat an operating system security dialog once per update is the single least reassuring moment in the product.

The Windows side has a smaller version of the same problem from the opposite direction:

"nsis": { "oneClick": false, "allowToChangeInstallationDirectory": true, "createDesktopShortcut": true, "createStartMenuShortcut": true }

Letting people choose the install directory is friendly, and on a reinstall it means a second copy can land somewhere else while the first stays where it was. Both copies read the same %APPDATA%\Notifio, so no data is lost and no two monitors fight, but the shortcut the user clicks tomorrow may still be the old binary, and nothing in either copy can tell them which is which. Which is, again, the version problem.

What I am doing about it

Not writing an auto-updater. Reinstalling is a perfectly good update mechanism for software that changes four times a year, and the thing that makes it bad right now is not the download, it is that the product cannot answer "am I current?".

So, in order: the version string goes into the window and into the licence check, the licence check response gains the latest version so the app can say one sentence about it, and the release script gets the four-line assertion about productName. The three phantom paths come out of the packaging config at the same time, because a packaging list that names files which do not exist is a list nobody is reading carefully.

If you want to see the end of this pipeline, the installers are on the download page, with three buttons and no user agent sniffing. The licence is a one-time purchase on the pricing page, the reinstall and background-running questions are answered on the help page, and the per-site setup pages are at notifio.app/alerts, including Kamernet and SpareRoom.

Why I built a YouTube timeline with no recommendations

📅 Nov 01, 2026  |  Category: Technology  |  Read Source →

TL;DR

  • I'd open YouTube to watch one video and lose an hour following recommendations. I never really tried to fight it.
  • So I built a page that shows only new uploads from the channels I pick, in upload order, with no recommendations and no Shorts.
  • Now I watch what's new and close the tab. That was the whole goal, and it works.

Plainfeed shows new videos from the YouTube channels you choose, in the order they were posted, without recommendations or Shorts. My last post was about running it on 10,000 API units a day. This one is about why it exists. It's short.

Where the time went

Nothing dramatic. I'd have a video in mind, open YouTube, watch it, click the one next to it, go back to the home page, find another one. After a while I'd be deep into videos that had nothing to do with why I came. The problem wasn't that the algorithm picked badly. It picked well.

The subscriptions tab didn't fix it either. Watching new uploads from the top, one by one, worked fine, but once I got to the end, autoplay would queue up videos from channels I didn't follow. Right when I thought I was done, the recommendations came in through the back door. Shorts were mixed in along the way, too.

A lot of people seem to have the same problem. A post I read recently on a community forum described opening YouTube for one long video and forgetting about it because of Shorts and thumbnails. The question was whether any habit or software could help.

What I didn't try

Honestly, I didn't try the usual fixes. Deleting the app, turning off notifications, installing a screen-time extension. They all felt like a fight I'd have to win every single time. The temptation stays on the screen; only my willpower changes.

I figured if the temptation wasn't on the screen, there'd be nothing to fight. YouTube without recommendations. That was the whole idea.

What I built instead

In short: I put time where the recommendations used to be.

  • Only new uploads from channels I pick, stacked in upload order. Nobody chose the order; the clock did.
  • Shorts are filtered out. Watched videos change their marker and can be hidden, so the list empties as you go. When it's empty, you're done.
  • No "up next" beside the player. When a video ends, there's nothing to do. That's on purpose.
  • No sign-in. Paste a channel URL and it works.

The key was a list with an end. A recommendation feed has no end, so there's no natural point to stop. New uploads from the channels you follow are a handful a day, and once you've seen them, closing the tab is the obvious next move.

What surprised me

I didn't expect so many Shorts. Of the 590 most recent videos across my 40 channels, 153 were Shorts, about 26% (October 2026, measured for my last post). Channels I thought of as long-form were posting Shorts in between. Filtering them out made the list noticeably shorter, which means I reach "all caught up" sooner.

What I didn't build

  • No screen-time limits or timers. Watch as much as you want; just don't get dragged along.
  • No attempt at "better recommendations." The goal was to remove them, not improve them.
  • It's not a YouTube replacement. If I want to search or browse, I go to YouTube. This is one window for new uploads from channels I follow.

Closing

I'm happy with it. I open it, watch what's new from the channels I care about, and close it. Not a big life change, but I no longer forget what I came for.

Security, safety, robustness and privacy are four different problems

📅 Nov 01, 2026  |  Category: Technology  |  Read Source →

Teams often file every AI risk under one word, usually "security" or "safety", and then argue about whether a guardrail has dealt with it. The four concerns are related, but they ask different questions, need different evidence, and usually belong to different people.

  • Security asks whether an actor can violate confidentiality, integrity, availability or authorized control.
  • Safety asks whether operating the system can cause unacceptable harm, including harm with no attacker involved.
  • Robustness asks whether behavior stays acceptable under noise, distribution shift, ambiguity or stress.
  • Privacy asks whether personal or sensitive information is collected, inferred, used, retained or disclosed appropriately.

One summarizer, three different failures

Take a model that summarizes clinical documents.

A malicious document instructs it to reveal another patient's record. That is a security attack, with privacy impact. A faithful summary leaves out a critical allergy because the scan was poor. That is a robustness failure, with safety impact. And a correct diagnosis, inferred where nobody authorized the inference, can be a privacy and governance failure with no attacker anywhere.

No single guardrail can prove all three cases are controlled. Treating the four words as synonyms produces controls too vague to test.

Different questions need different evidence

Question Discipline Representative evidence Can an untrusted document cause an unauthorized tool action? Security Taint-aware attack tests, policy decisions, egress and tool traces Can an allowed answer create unacceptable physical or social harm? Safety Hazard analysis, scenario tests, review and escalation outcomes Does quality hold under blur, accent, long context or missing data? Robustness Slice metrics, perturbation tests, calibrated abstention Can training or inference expose a person's data? Privacy Data inventory, minimization, access logs, deletion and privacy attack tests

Engineering Insight

Record the overlap, but keep accountability separate. Security may own exploitability and access controls, product safety the hazardous outcomes, privacy the lawful processing and minimization, and ML engineering the robustness. A shared risk register shows where they intersect; each claim in it still needs an owner, a test, a threshold and a response.

An architecture review that lists one "AI risk" control and calls the job done has usually tested one of these four. Asking which discipline a control serves, and what evidence would show it failing, is the quickest way to find the other three.

Reject Duplicate JSON Keys Before Validating a Record

📅 Nov 01, 2026  |  Category: Technology  |  Read Source →

AI and affiliation disclosure: An AI agent prepared this standalone technical article for TokenPeak. The inputs are invented teaching fixtures. Its Python examples were checked locally; no remote API, customer payload, or production parser was tested.

Consider a small JSON document containing the same member name twice:

{"decision": "review", "decision": "send"}

If your application validates only the dictionary produced by its decoder, the repeated name may already have disappeared. A check that the final value belongs to an allowed set cannot recover the ambiguity in the original document.

The Python 3.12 JSON documentation describes the default decoder's handling of repeated names and its hooks for customizing object decoding. For a record format that requires unique names, inspect the pairs while decoding instead of inspecting only the resulting dictionary.

Define a deliberately narrow input boundary

This teaching parser accepts a supplied string of at most 4,096 UTF-8 bytes and requires a top-level object. It rejects repeated member names, including inside nested objects. It also rejects the non-finite constant spellings accepted by Python's default decoder.

Decimal fractions become Decimal values so that a large finite exponent is not silently converted into a floating-point infinity. That is a representation choice, not permission to accept arbitrary numeric ranges in an application schema.

import json from decimal import Decimal def unique_object(pairs): result = {} for key, value in pairs: if key in result: raise ValueError("Duplicate object member") result[key] = value return result def reject_constant(text): raise ValueError("Non-finite JSON constant") def decode_record(text): if type(text) is not str: raise TypeError("Supply decoded text") if len(text.encode("utf-8")) > 4096: raise ValueError("Teaching input limit exceeded") value = json.loads( text, object_pairs_hook=unique_object, parse_constant=reject_constant, parse_float=Decimal, ) if type(value) is not dict: raise ValueError("Top-level object required") return value if __name__ == "__main__": assert decode_record('{"decision":"review"}') == {"decision": "review"} assert decode_record('{"amount":0.1}')["amount"] == Decimal("0.1") bad_inputs = [ '{"decision":"review","decision":"send"}', '{"nested":{"x":1,"x":2}}', '{"x":NaN}', '[1,2]', ] for text in bad_inputs: try: decode_record(text) except ValueError: pass else: raise AssertionError("Expected rejection") print("6 local cases passed")

Save this block as decode_record.py and run it with Python without optimization flags, which can disable assertions. The exact block was run during preparation on Python 3.12.14. Its six cases exercise accepted objects, decimal representation, duplicate detection, non-finite constants, and the root-type rule.

Check ambiguity before business meaning

The object hook receives the member pairs before this function constructs its dictionary. Each nested object goes through the same hook. A repeated x in a child object is therefore rejected even when the outer object has unique names.

After this boundary, application validation still has work to do. The parser accepts an object with a single decision value of "launch spacecraft"; it does not define the business vocabulary. It also does not establish whether an integer is a valid identifier or whether a decimal lies within an allowed range.

Keep those stages separate in tests. One test can ask whether the document is unambiguous under your decoding policy. Another can ask whether the decoded record satisfies your domain contract. Their failure messages can then tell the caller which decision failed.

State what the size check cannot guarantee

The string already exists in memory before this function checks its encoded length. This is not a bounded network reader. It does not impose a nesting-depth limit, a numeric-digit policy, or a total CPU budget. A production boundary needs limits appropriate to its transport and parser.

The function deliberately raises an error without echoing the entire input. That keeps this particular exception message small; it is not a comprehensive logging or secret-redaction guarantee.

The practical lesson is about preserving a validation opportunity. Once decoding has collapsed repeated names into one dictionary entry, a later schema check may be too late to ask whether the original document supplied one answer or several competing answers.

Eight entries in one content array, 1,041 to 2,034 words each, and the optional field that has exactly one user

📅 Nov 01, 2026  |  Category: Other  |  Read Source →

Munchable covers eight digestive conditions, and each one has a guide page. All eight are entries in a single array of a single interface, server-rendered at build time, so the index and every guide under it come out of one file.

That makes them comparable, which is the only reason this post exists. Content you can measure against itself tells you things that content in a CMS never will.

The inventory

I counted the source entries and then counted the live pages. Sorted by the live word count:

guide src lines sections FAQs words links in HTML answers linking in coeliac disease 87 4 5 2,034 125 88 bile acid malabsorption 54 3 3 1,543 103 67 low FODMAP and IBS 55 3 3 1,338 100 64 lactose intolerance 47 2 3 1,257 88 52 SIBO 41 2 2 1,168 100 64 IBD 49 3 2 1,126 84 48 GERD and reflux 51 3 2 1,075 80 44 gastroparesis 44 2 2 1,041 70 34

The links column counts every internal link in the page's HTML, so about 30 of each row is the header and footer that all 516 of our pages share. The last column is the number of ingredient answer pages that link back to that guide.

The top row is 95 per cent longer than the bottom row. It has twice as many source lines, twice as many sections, and more than twice the FAQ entries. It was also the last one written, which is the part that matters, because nothing in the type or the tests asked it to be bigger. It is bigger because it was written on a day when we knew more about writing these than we did for the first one.

The other seven do not form any pattern at all. They are not ordered by how common the condition is, or by how old the page is, or by anything else I can find. They are each as long as the afternoon they were written, which is what a content set with no floor looks like when you finally line it up.

The optional field

Here is the part of the interface that interests me:

export interface ConditionPage { slug: string; condition: ConditionId; name: string; h1: string; metaTitle: string; metaDescription: string; lede: string; summary: string; sections: ConditionSection[]; checks: string[]; faqs: { q: string; a: string }[]; furtherReading?: { href: string; label: string; inline: string; blurb: string; }[]; }

Eleven required fields and one optional one. The optional one has exactly one user out of eight entries, and it was introduced by the entry that needed it: coeliac disease has head terms that are a vocabulary rather than a question, so it got a reference page of its own, and the guide needed somewhere to point at it from.

That is a perfectly reasonable thing to do, and it is also the exact mechanism by which content types rot. A required field is a question every entry has to answer. An optional field is a note that one entry had something extra to say. Add enough of them and the type describes the union of everything anybody ever wanted to publish, no single entry is ever incomplete, and nothing fails when a page is thin.

The alternative shape would be a separate registry keyed by condition, which makes the asymmetry visible in a file of its own rather than invisible as an absent property. I do not think that is better here, because further reading genuinely belongs next to the guide it extends. But it is worth naming the trade, because "make it optional" is the default move and it has a cost that arrives later, in a column of numbers like the one above.

The thinnest page is also the least linked

Look at the last two columns together. Each of the 461 ingredient answer pages links back to the guide for its condition, so the inbound count is a property of how many ingredient questions that condition has pages for. The spread is 88 down to 34.

Those two columns are nearly the same ranking. The condition with the most to say got the longest guide and 88 internal links pointing at it. The one with the least got the shortest guide and 34. Nobody decided that, and it compounds in the wrong direction: the page most in need of help getting found has the least help, and the page that already reads best is the one the rest of the site keeps recommending.

This is the thing I would not have noticed from inside the editor. Both numbers look fine on their own. It is only when you print them in the same table that you see the site has a quiet preference.

What a floor would actually look like

The temptation is a word count minimum, and it is a trap. A test that fails under 1,200 words produces 1,200 words, and the last 160 of them will be padding that makes the page worse.

A structural floor is defensible: every guide has at least three sections and at least three FAQ entries. Those are not quality, but they are shape, and shape is the thing that drifted. We already enforce an upper bound on the other end, a title and description budget read out of the source files by a test, so the machinery for this exists and is one assertion long.

The real remedy is not a test, though. It is going back to the first seven pages with what we learned writing the eighth. The useful output of an audit like this is not a CI rule. It is a list, in order, of which page to fix first, and that list is just the table above read from the bottom up.

If you want to see the two ends of it, the longest is the coeliac guide and the shortest is the gastroparesis one. Same template, same type, same build, 993 words apart.

Introduction

No exploit. No payload. No shell. The entire "challenge" lives in a browser's View Source and it took longer to write this sentence than it took to solve the box. That sounds like a joke, but it's actually the most important lesson in this whole series: if your authentication logic runs in the browser, it's not authentication, it's a suggestion the attacker is free to ignore.

CyberHeroes has the audacity to call itself a challenge while leaving its front door not just unlocked, but labelled "FRONT DOOR" in neon letters. It's a single-page portfolio site with a login form that genuinely believes security is a server-side problem. Spoiler: they didn't check with the server. If this box were a bank, the vault combination would be written on the outside of the vault in permanent marker. It's that kind of day.

Recon

Same opening move as always — RustScan for speed, Nmap for detail.

rustscan -a 10.49.154.83 -r 1-65535 --ulimit 5000 -- -Pn -sC -sV Port Service Version 22/tcp SSH OpenSSH 8.2p1 Ubuntu 4ubuntu0.4 80/tcp HTTP Apache httpd 2.4.48 (Ubuntu)

Two ports, nothing exotic. Apache 2.4.48 is not ancient like some of the others in this series — this one isn't about outdated services. The HTTP title comes back as CyberHeros : Index. Typo in the page title is always a great sign of quality software engineering.

Feroxbuster with PHP, TXT, and HTML extensions across the medium wordlist:

feroxbuster -u http://10.49.154.83/ \ -w /usr/share/wordlists/seclists/Discovery/Web-Content/DirBuster-2007_directory-list-2.3-medium.txt \ -x php,txt,html # output (relevant hits only) 200 http://10.49.154.83/index.html 200 http://10.49.154.83/login.html # ^^^ this is where the fun is 200 http://10.49.154.83/changelog.txt

(truncated — the rest was asset files: images, vendor JS/CSS, nothing actionable)

login.html is the obvious next stop. changelog.txt is worth a read — it appeared to be a generic template changelog with no sensitive information — so the login page it is.

Foothold

Authentication is supposed to be validated on the server — a system the attacker cannot directly inspect or manipulate. When a developer moves that logic into client-side JavaScript, they've handed the attacker the padlock, the key, the combination, and a handwritten note explaining how the lock works. The browser must download and execute all JavaScript to render the page — which means the attacker can read every line of it before touching a single input field.

Navigating to login.html and hitting Ctrl+U (View Source) immediately reveals the authenticate() function:

function authenticate() { a = document.getElementById('uname') b = document.getElementById('pass') const RevereString = str => [...str].reverse().join(''); if (a.value=="h3ck3rBoi" & b.value==RevereString("54321@terceSrepuS")) { var xhttp = new XMLHttpRequest(); xhttp.onreadystatechange = function() { if (this.readyState == 4 && this.status == 200) { document.getElementById("flag").innerHTML = this.responseText ; document.getElementById("todel").innerHTML = ""; document.getElementById("rm").remove() ; } }; xhttp.open("GET", "RandomLo0o0o0o0o0o0o0o0o0o0gpath12345_Flag_"+a.value+"_"+b.value+".txt", true); xhttp.send(); } else { alert("Incorrect Password, try again.. you got this hacker !") } }

Breaking this down:

  • Username is hardcoded in the comparison: h3ck3rBoi
  • Password is the string 54321@terceSrepuS passed through RevereString(), which reverses it character by character — yielding SuperSecret@12345
  • On success, the script constructs a GET request to a .txt file at an "obscure" path that's... right there in the source, assembled from the username and password values

The credentials, the reversal algorithm, and the flag's file path are all completely readable before submitting a single form field.

Username Password Where Found h3ck3rBoi SuperSecret@12345 login.html JavaScript source

Substituting the known credential values into the path template from the JS:

RandomLo0o0o0o0o0o0o0o0o0o0gpath12345_Flag_h3ck3rBoi_SuperSecret@12345.txt

This file can be fetched directly without ever touching the login form:

curl "http://10.49.154.83/RandomLo0o0o0o0o0o0o0o0o0o0gpath12345_Flag_h3ck3rBoi_SuperSecret@12345.txt"

Or simply by entering the credentials into the login form, which triggers the XHR fetch and injects the response into the page.

No shell required for this challenge. Access to the flag was achieved entirely via browser interaction with the login page after reading the client-side source.

Key Takeaway

Anything that runs in the browser is readable by the user — no amount of string reversal, obfuscation, or "obscure" path names changes that. Authentication logic belongs on the server, full stop.
