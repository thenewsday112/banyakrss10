The agent has finished the bulk of your change. Now you want to inspect one implementation detail, adjust a few lines by hand, and run the project locally before you ship it.

But the work is sitting in the GitHub Copilot app… and your editor is where you review diffs, debug code, and make final adjustments. Do you have to choose between staying in the session and starting over in Visual Studio Code?

You don’t. You can open the Copilot app session directly in VS Code and continue with its conversation, code changes, and working context intact. That means Copilot can handle the repetitive or time-consuming work, then hand control back to you for closer review, hands-on editing, and local testing.

In this tutorial, you’ll learn how to:

  • Open a Copilot app session in VS Code.
  • Review the agent’s changes line by line.
  • Continue the same conversation from your editor.
  • Modify and test the code locally.
  • Push your updates to the pull request associated with the session.

Prerequisites 

Before you begin, make sure you have: 

  • The GitHub Copilot app installed and signed in. 
  • Visual Studio Code installed and connected to the same GitHub account. 
  • A Copilot app session with code changes you want to review or continue. 
  • Permission to work in and push changes to the session’s repository. 

This tutorial assumes you are already comfortable navigating VS Code, running commands in its integrated terminal, and working with Git branches and pull requests.

1. Start with a session in the Copilot app

Open the session you want to continue. Before handing it off, take a moment to review the task and the work Copilot completed.

A session contains more than a collection of modified files. It also records the task, the plan, and the conversation that produced those changes. That context is important when you want to understand why Copilot chose a particular implementation or ask it to revise part of the work.

You do not need to summarize that history or copy it into a new chat before moving to VS Code.

2. Open the session in VS Code

From the session, select Open in VS Code. If the app presents more than one supported editor or VS Code installation, choose the one you want to use.

VS Code opens the project using the worktree associated with the session. It also displays the existing session in the Copilot sidebar.

That gives you three connected pieces of the original work:

  • The session context: The task, plan, and conversation remain available.
  • The diff: The files and lines changed by the agent are ready for review.
  • The worktree: VS Code opens the same isolated working tree the session used.

You are continuing the existing session, not reconstructing it in a new editor window.

3. Review the agent’s changes

Before editing, inspect the diff in VS Code. Open the Source Control view to see the changed files, then select a file to review its changes line by line.

Review the implementation as you would any other proposed change. In particular, check that:

  • The code solves the requested problem.
  • The implementation follows the repository’s conventions.
  • Error states and edge cases are handled appropriately.
  • Tests cover the behavior that changed.
  • No unrelated files or behaviors were modified.

The preserved conversation can help explain how Copilot arrived at the implementation. If something is unclear, continue prompting Copilot in the sidebar. For example:

Explain why you changed this function instead of adding a new helper. Identify any behavior this could affect.

You can also ask Copilot to make another change. Because the session and worktree remain connected, you do not have to describe the task from the beginning.

4. Make a hands-on edit

Once you understand the proposed changes, edit any file directly in VS Code.

This is useful for adjustments that are faster or easier to make by hand, such as:

  • Refining a label or error message.
  • Renaming a variable for clarity.
  • Adjusting layout or styling.
  • Adding a missing test case.
  • Applying a repository-specific convention.

You are editing the session’s existing worktree, so your manual changes build directly on the agent’s work. You do not need to copy files between directories or manually re-create the branch.

5. Run and verify the project locally

Use the VS Code integrated terminal to run the project’s normal validation workflow. The exact commands depend on the repository, but some web app examples may include:

  • npm install
  • npm test
  • npm run lint
  • npm run dev

Treat agent-generated changes the same way you would treat code written by a person: run the relevant tests, inspect failures, and verify the behavior yourself.

If the development server prints a localhost URL, open it to test the change in a browser. When supported by your VS Code setup, you can open the URL in VS Code’s integrated browser and inspect the result without leaving the editor.

For a user-interface change, verify both the requested behavior and nearby states. For example, check the modified component at different viewport sizes and confirm that loading, empty, and error states still work.

6. Continue with Copilot or keep editing yourself

At any point, you can choose the interaction that best fits the next step:

  • Prompt Copilot when the change requires repository-wide analysis or repetitive edits.
  • Edit directly when you know the exact change you want.
  • Use both approaches iteratively as you test and refine the implementation.

For example, after making a manual UI adjustment, you might ask Copilot:

Add a test for the updated label and run the relevant test file. Do not modify unrelated components.

Because you are still in the original session, Copilot retains the context needed to interpret “the updated label.”

7. Commit and push the finished changes

When the implementation is ready, review the final diff one more time. Then commit and push the changes using the Source Control view or the integrated terminal:

  • git status
  • git add
  • git commit -m "Refine session changes"
  • git push

Use your repository’s normal branch, commit, review, and approval practices. Because VS Code opened the worktree and branch associated with the session, pushing the branch updates the pull request already tracking that work.

There is no need to copy the finished files into another checkout or reconnect the work to the pull request manually.

A continuous workflow from agent to editor

Opening a Copilot app session in VS Code gives you a clean division of labor without splitting the work itself. Copilot can take on a larger or repetitive implementation, while you can move into the editor for detailed review, targeted changes, local testing, and final polish.

The session, diff, and worktree move with you. Start by directing the work in the Copilot app, switch to VS Code whenever you want hands-on control, and push the finished result through the same pull request workflow.

Ready to try it? Download the GitHub Copilot app, start a session, and open it in VS Code when you are ready to continue coding.

Is Your Organization Messing Up AI Adoption?

📅 Oct 16, 2026  |  Category: Technology  |  Read Source →

The way I see most organizations roll out AI feels more like a farce than a strategy. If it were turned into a movie, reviewers would say it was unbelievable. Nobody could be that stupid.

Yet here we are. And what makes it all the more frustrating is that we have been here before.

Back in 2014, I wrote a book for Smashing Magazine called Digital Adaptation, looking at the mistakes being made in how organizations were approaching digital transformation and what they should be doing instead. The similarities between then and now are striking.

So in this post, I want to look back at Digital Adaptation and see how the lessons in that book apply to the AI era and what we can learn from the past to help us navigate the challenges of AI today.

The biggest mistake, both then and now, is approaching each as a technological challenge.

It’s About People, Not Technology

Sure, both digital transformation and AI are technological advances, and yes, some level of technological implementation is required. But that is the tip of a very large iceberg.

Back in the midst of the digital transformation era, IT departments were rolling out CMSs, CRM systems, intranets, and so on. Meanwhile, on the customer-facing side, organizations were rolling out websites, apps, and personalization. But they were putting almost no emphasis on how people were going to use these systems.

Internal systems were hard to use, and customers either didn’t care what was being built or wanted something else entirely.

The same is happening with AI. Senior management are buying into the hype, and IT teams are rolling out Copilot Studio licenses company-wide and considering the job done. Sure, there is a bit of organization-wide generic training, but that’s about it.

Just like before, staff are left wondering what to do with these new systems and feeling under pressure to use them and deliver results.

Organizations need to recognize that AI is a cultural shift as much as a technology, and that shift has enormous implications for their staff.

After all, this time around, it is even worse, because this time, staff fear for their jobs. They have read the same headlines that you have, and no amount of promises from senior management is going to make them feel any better.

Why Would Staff Want To Adopt AI?

I mean, think about it from a staff member’s point of view. AI offers them very little personally, even setting aside the fact that management may be intending to use it to replace them.

The main reason senior management are excited about AI is that it provides additional productivity. People can do more in less time. But that does not benefit staff. They are still required to work 9 to 5, but now they are expected to do more in the same time. They don’t get any time back, and they don’t get paid more, so why would they embrace AI?

So before asking staff to embrace AI, organizations need to ask themselves how they intend to motivate them to do so.

One strategy is to help staff identify the parts of their job they hate and how AI can help them do those tasks more quickly and less painfully. People tend to be a lot more receptive to change when it is presented as an opportunity to improve their working lives.

But, that should just be the beginning. Organizations may need to consider providing incentives for staff to adopt AI in terms of career progression, compensation, or shorter working hours.

Staff Need Time And Support To Adopt AI

Also, adopting AI is not a simple task. It involves challenging every working practice they have built up over (in some cases) decades. All of that procedural knowledge has to be rebuilt. That is a lot to ask of anybody in even the best of circumstances, and most employees do not find themselves in the best of circumstances.

Most are overworked and struggling to stay on top of their to-do lists. They don’t have time to sit down, learn a new tool, and figure out how it fits into their workflow.

That doesn’t just take time. It also takes a lot of consideration and experimentation. It is not enough to just send a member of staff on a training course and expect them to be able to use AI to its full potential.

At a minimum, staff need training specific to their roles, such as the AI training I provide to UX teams. But organizations should be going even further.

They need to develop sophisticated training programs that help staff from different departments understand how to use AI in their specific roles. They need ongoing support and the time to experiment with AI to find the best ways to use it.

But formal training will only take you so far. In my experience, the most effective support comes from colleagues, which is why I would start with the enthusiasts rather than the resisters. Every organization has a handful of people who are already experimenting with AI, often without anybody asking them to. Bring those people together, give them the time and space to share what is working for them, and let their enthusiasm spread to everyone else.

I saw this work during the digital transformation era too. In Digital Adaptation, I described an internal conference where staff showed their colleagues what they had built, and it did more for adoption than any memo from the top ever could. People are far more likely to try something when they see a colleague in a similar role using it successfully than when they are told to by senior management.

Rather than trying to win over the most resistant staff first, organizations should find the people already experimenting with AI, give them time to share what they have learned, and let social proof do the heavy lifting.

Unfortunately, experimentation comes with a big downside… mistakes will be made.

It Needs To Be Safe To Fail

Many organizations have, to be frank, a culture of fear where mistakes are seen as a sign of incompetence. However, by its very nature, learning a new tool like AI will involve making mistakes, and this can be a massive barrier to adoption.

I saw this during the era of digital transformation. Senior management would demand digital transformation and were confused when it didn’t happen.

What they didn’t realize was that they were sending mixed messages to staff. Sure, they were asking for digital transformation, but they were still demanding that the same key performance indicators (KPIs) be met, and they still pointed out any mistakes in their annual reviews.

There was no space to fail, as the pressure to deliver was relentless.

This time around, it seems to be even worse. I hear horror stories of staff being reprimanded for using too many tokens just weeks after being told to adopt AI. Or staff being lectured so much about what they should or should not do with AI that they are afraid to try anything. It is safer to just do what they have always done.

If management want staff to adopt AI, then they need to make staff feel safe to experiment. They need to adjust KPIs, change how staff are reviewed, and relax some of the governance while staff are learning.
Handle Governance With Care

Look, I get it. AI cannot be rolled out without some governance in place, but again, this is an area that organizations have typically handled poorly.

In the midst of digital transformation, governance would either be non-existent, or it would be so strict that it would stifle innovation, and unfortunately, I see the same pattern emerging with AI adoption.

Staff need some governance to help them know where they stand. It helps them understand what is expected of them and what they can and cannot do.

But too often organizations have been so strict that it is easier not to do anything at all. Pages of instructions about what people should and should not share with AI create that sense of fear that I mentioned earlier.

Organizations need a short set of principles that would fit on a handful of posters, similar to gov.uk’s design principles. Beyond that, they need to demonstrate a degree of trust in their staff to use common sense.

Of course, mistakes will get made, but that is the cost of change, and so organizations need to accept that and do what they can to mitigate that in how they roll out the technology.

Adaptive Technological Rollout

That said, organizations will need to be careful in how they roll out AI from an IT perspective. Once again, it is easy to lock everything down and stifle the adoption of AI.

Again, this is something I highlighted back in 2014 with digital transformation. Overstretched IT teams would pick a set of technologies and roll them out organization-wide, often with little or no consultation with the individuals who would be using them. Anything outside of that set of technologies had to go through a complex approval process, normally involving a steering committee. The result was a glacial pace of change that was one of the major contributing factors to the failure rate of digital transformation projects.

Today we are seeing the same thing. IT teams are opting into a tool like Copilot and calling it a day, but that often falls massively short.

Take, for example, a UX team I am working with at the moment. Management is pushing hard for AI adoption, and the team is excited about the potential of creating an AI-powered research repository and even AI personas. It sounds like a wonderful case study in AI adoption, with enthusiastic management, an excited team, and innovative ideas.

Unfortunately, the reality is that nothing is happening because Copilot cannot deliver on the team’s vision, and so they are currently bogged down in bureaucracy as they try to persuade the AI steering group that they need to use a different toolset. Understandably, the team’s enthusiasm is waning. Why bother?

And that team is one of the more patient ones. In many organizations, staff are not waiting for the steering group at all. Just as we saw shadow IT during the digital transformation era, with people signing up for Dropbox and Google Docs because the official tools could not do what they needed, we are now seeing shadow AI. When the in-house AI tool will not let people do their jobs, they open a personal ChatGPT or Claude account on their phone or home laptop and get on with it.

That is far more dangerous than the problem the restrictions were meant to prevent. Company data ends up in tools the organization has no control over, with no oversight and no record of what has been shared. In trying to lock everything down, organizations end up pushing the risk somewhere they cannot see it.

The instinctive reaction is to clamp down with stricter policies, blocked websites, and warnings about disciplinary action. But that rarely works, and it drives the behavior further underground. Shadow AI is a symptom, and a useful one, because it shows exactly where the official tools are falling short.

Instead of trying to stamp out shadow AI, organizations should learn from it. Talk to staff about what they are using personal accounts for and what they feel they cannot do with the AI they have been given, then use that to shape what gets rolled out next.

Look, I understand the cost of a messy, out-of-control tech stack. It is not ideal. However, in the early days of adoption, we may have to live with a bit of chaos while people explore the edges of what is possible and work out common use cases.

Organizations need to allow staff to explore different uses of AI and even different AI apps to find what suits their specific needs in their specific roles. They can always start locking things down later as the real organizational needs become clearer.

A Dangerous Time

I admit all of this feels dangerous to some organizations. They want to control the AI adoption process centrally and make sure nothing goes wrong. I understand that. But change comes with a degree of risk, and the risk of moving too slowly is greater than the risk of moving too fast.

However, a bigger danger still is when organizations see this as a technological challenge and overlook the human side of things. AI adoption is not simply about rolling out new technology. Just like digital transformation, it is about people, culture, and change management. The sooner organizations realize the scope of what they are dealing with, the better.

You can often tell whether a post was written by AI or a person, but can you put your finger on why? Try to spot as many signs of AI slop as you can in this pull request (PR) description:

This PR introduces a robust caching layer for Panel’s reactive pipelines. It’s not just a performance improvement — it’s a fundamental shift in how state flows through your app. By leveraging memoization, we seamlessly reduce redundant computation, improve responsiveness, and lower server costs. Ultimately, this change empowers developers to build faster, more scalable dashboards.

If you spotted “robust,” “leveraging,” “seamlessly,” and “empowers,” those are some common ones, but swapping those words out would still leave a paragraph that reads like AI, because the rest of the problems are structural:

  • “It’s not just X, it’s Y” argues against a claim nobody made.
  • “Reduce redundant computation, improve responsiveness, and lower server costs” is a list of three because three sounds complete, not because there are three measured benefits.
  • The last sentence restates the first with bigger words.

Delete everything that isn’t information and very little is left:

Adds memoization to the reactive pipeline.

The PR paragraph marked up by pattern, with the one-line rewrite

This matters beyond style, since a reader who spots AI slop starts doubting the whole document, including the parts someone wrote carefully. For a PR description, that means the reviewer trusts the code a little less before reading a single line of it.

Ironically, Claude helped me draft this post about AI slop, so I’ll let you judge how that went. Most of what follows comes from multiple passes I made flagging slop in its drafts, and some of those fixes went back into a deslop skill under holoviz-skills.

Best practices for writing PRs

  • What makes text read as AI-written is flowery vocabulary like “delve” or “robust” in place of simple, straightforward terms, but AI patterns also include structure, like announcements, “not X but Y,” triplets, restatements, short choppy sentences, tidy closers, and heavy formatting. Swapping out words alone won’t fix all the issues.
  • The most effective fix is giving the model an example of the voice you want before it writes.
  • To clean up a draft, delete before rewriting, run a scanner (like the one under the deslop skill) for the mechanical patterns, and reread for what it missed. Then, rewrite after honing your prompt, or write the draft in your own words.
  • Last, have another human review it and ideally, read it out loud.

Common pitfalls

  1. Announcing something instead of saying it, with openers like “Here’s the thing,” “The key insight is,” “It’s important to note that,” and “Let’s dive in,” where the fix is to delete the promise and keep the content:
    It’s important to note that the parser is single-threaded. → The parser is single-threaded.
  2. Contrast framing like “It’s not a tool; it’s a workflow” or “Not just faster, but cheaper” needs a wrong answer to push against, so the model makes one up, and the fix is to state the second half, or if both halves are real, join them into “faster and cheaper.”
  3. Triplets like “fast, flexible, and scalable” show up because three has rhythm, so count the items that are true and keep only the ones you can back up and that aren’t repetitive.
  4. Repeating the same point in new words, like, “The parser is slow. It takes a long time to run. Why is it so sluggish?” which says one thing three times, so keep the clearest version and cut the rest.
  5. Short choppy sentences in a row, like “Banning words half works. Models find substitutes,” chops one idea into beats to sound decisive. Joining them with the connective they were hiding (“since,” “so,” “but”) usually reads better.
  6. Tidy closers like “Ultimately, it’s about building better software” or “And that changes everything” add a sense of finish without adding information, so if the last sentence restates the first or adds empty emphasis, cut it.
  7. Formatting as effort is bold labels on every bullet, headers over sections only two paragraphs long, and tables where a sentence would do.
  8. Vague authority and passive voice attribute a claim to someone who isn’t there (“experts argue,” “many believe,” “mistakes were made”) or add “on the other hand” when one side is clearly right, so name the source or own the claim.

Why models write like this

One likely reason: during fine-tuning, people rate responses. Structure, balance, and emphasis all read as effort, so the model learns to add them everywhere, including where they carry nothing. It also leans toward the most common style in its training data, which includes a lot of marketing copy. A person adds a flourish when a sentence needs it while a model adds one every few sentences regardless.

While writing this, I asked Claude what makes large language model (LLM) writing recognizable, and its answers came back as bold-labeled bullets under headers, ending on tidy one-liners. When I asked whether its own answers were slop, it found the not-X-but-Y pattern it had used while explaining why not-X-but-Y is bad. It’s better at spotting the patterns than avoiding them, which makes it more useful as a reviewer than as a writer.

How to deslop

Before you generate

An example of your writing beats any list of instructions, so paste a paragraph of your own writing, or one you’d like to sound like, and ask for that voice, since, in my experience, models imitate examples far more reliably than they follow adjectives like “concise” or “natural.” (This is how the draft of this post started: I handed Claude my last post and said “this is my tone of voice.”)

It also helps to describe the reader, since “the reader already maintains a Panel app” cuts the warm-up explanations.

Then, describe what you want rather than what to avoid, because “don’t sound like AI” is vague.

Model choice matters too. On the same diff, Claude Opus 5 sounded archaic, while Claude Opus 5.5 was much easier to read.

After you generate

Delete first, since most slop is extra words. Openers, closers, hedges, and announcements carry no information, and the LLM can’t replace them with new slop.

For the mechanical patterns, a scanner catches them consistently, and the deslop skill in holoviz-skills includes a scanner:

python3 scripts/deslop_scan.py draft.md

It flags phrases and sentence patterns, and --em-dash and --colon-triple turn on two checks that are noisy in technical writing. It has false positives (a legitimate “no X, no Y” in quoted dialogue, say), and it can’t see a paragraph that tries to sound deep without tripping a regex. So the skill pairs the scan with a judgment pass: read the whole piece, fix hits one at a time, then re-scan and justify every hit that’s left.

Reading it aloud also works, since triplets and restatements are obvious when spoken.

If you control the model, fine-tuning is another option: train it against a reward that scores slop, so it writes less of it to begin with. Sophia Yang’s first reinforcement learning (RL) run with the Jev reward model is a good place to start.

What not to do

Banned-word lists help at the margins, but models route around them, so ban “delve” and you get “dig into,” and a rewrite that swaps “Here’s the thing” for “The reality is” hasn’t fixed anything.

Don’t sand your voice down to neutral either: if you write short punchy sentences or like an occasional emoji (guilty ), keep them.

And if a draft is slop from top to bottom, an edit pass gives you a slightly cleaner bad draft, so start over with an example of the voice you want.

Wrapping up

The deslop skill and scanner are in holoviz-skills, but they only get you part of the way, so it’s still important to review the result yourself before it goes out, and if you find slop that slipped through in this post, let me know by posting them on the forum.

Working with outside collaborators can add more work for a repository owner. You need to confirm who still needs access, change permissions as projects evolve, and archive repositories once they’ve served their purpose.

To keep up, repository owners need to track collaborators, deadlines, and follow-ups for each repository. As a project grows, that manual housekeeping becomes harder to keep up with and easier to defer.

We faced this problem in a shared organization where GitHub employees (“Hubbers”) collaborate with customers and partners on product trials and professional services engagements. Our answer was Evergreen, a GitHub App built with native GitHub features. The workflows below exhibit a pattern you can adapt for your own organization.

Meet Evergreen

Evergreen is a GitHub App that automates organization hygiene through two workflows:

  1. Outside collaborator access reviews. Every quarter, each repo’s outside collaborators are reviewed. Keep who you need, and everyone else is removed.
  2. Stale repository detection and archival. Repos with no human activity past a threshold get flagged, warned, and (if still untouched) archived.

Two design principles shaped everything:

Fail secure. If nobody responds to an access review, we don’t leave access in place and hope for the best. We revoke it. The safe outcome is the default outcome.

Never destroy anything. Evergreen will never delete a repository or its contents. Archived repos are recoverable, and every access change is written into the repo’s tracking issue, so reverting a mistake is as easy as a copy-paste to Copilot.

How it works: One brain, many hands

Under the hood, Evergreen is a small Go webhook server running in a container. But the interesting part is the choreography. Every moving piece is a stock GitHub feature: a GitHub App, scheduled actions, webhooks, issues, custom properties, and plain files in a repo. Nothing exotic to reinvent.

A controller that keeps time

A dedicated controller repo acts as Evergreen’s clock and its memory. Four scheduled GitHub Actions workflows fire repository_dispatch events on a quarterly cadence, and the app wakes up and does the work:

Reviews open two weeks before their cleanup runs, and there’s a hard grace period baked in so a stray manual run can never fast‑forward the guillotine. Each workflow also supports workflow_dispatch, so we can trigger any step by hand as needed.

State you can git blame

Evergreen tracks every repo’s status as a JSON file (one per repository) committed to the controller repo under state/repos/<repo_id>.json. The snapshot of who had access, when the review opened, the deadline, who decided, and what happened all lives there. Here’s a completed review where a Hubber kept Alice’s access and let Bob’s lapse:

The best part: because state is just files in git, the commit history is the audit trail. Want to know why someone lost access last spring? git log the state file. There’s no separate database or bespoke audit pipeline to track.

Issue‑ops, everywhere it matters

Evergreen does its talking through issues inside each repository. When an access review kicks off, every repo gets a checklist issue:

The interaction model is delightfully simple: check the boxes for who stays, then close the issue. That’s it. When the issue closes, Evergreen listens for the issues.closed webhook event, reads the checkboxes, retains the checked collaborators, and revokes the rest, then posts a receipt comment listing exactly what it kept and what it removed.

Only the right humans can pull the lever

Closing an access review issue is a privileged action, so Evergreen guards it. If someone who isn’t a Hubber closes an issue, the app quietly reopens it and posts a note explaining why. Decisions only count when they come from the people authorized to make them.

Informing the right people

Here’s a subtle problem: we know the people who need to respond to a review are Hubbers, but we didn’t always know which Hubber(s) owned a given repository.

Evergreen resolves the right people to notify through a fallback chain:

  1. If a repo sets an evergreen_repo_owner custom property (a @user or @org/team), use it.
  2. Otherwise, look at recent issue and commit authors and cc the ones who are on the access review team, i.e., the Hubbers actually working in that repo.

The result: the right owners get pinged automatically, without anyone maintaining a spreadsheet of “who owns what.”

Fail secure, and fail closed

When a review deadline passes with no response, cleanup revokes every collaborator in the snapshot. We were careful about a subtle edge case: what if some removals succeed while others hit a transient API error? Marking the review “done” while a removal is still outstanding would be a quiet inconsistency, and we didn’t want that.

So Evergreen fails closed. If any removal fails, the review stays pending and the issue stays open, and the next run retries the stragglers. It only records “revoked” once every removal actually succeeded. And whatever gets removed is written into the issue, so restoring access is a matter of re‑adding the handles it listed.

The user experience: automation that feels considerate

Automated housekeeping has a reputation for being the office smoke alarm: loud, easy to ignore, and usually going off while you’re cooking something perfectly fine. We worked hard to make Evergreen feel like the opposite:

  • It comes to you. The work happens as an issue in your repo.
  • It tags the right people. No “who owns this?” archaeology.
  • It’s crystal clear about the ask. Every issue states what to do, the exact deadline, and precisely what happens if you ignore it.
  • It nudges before it acts. A reminder comment lands before the deadline: no surprise revocations.
  • It has an escape hatch. Org owners (Hubbers) can opt out by setting a custom property (evergreen_exempt_from_access_review or evergreen_exempt_from_archive).

Rolling it out carefully

Automation that manages access and archives repositories deserves a careful rollout, especially into a large, active org (ours has 1,400+ Hubbers, and many more customers and partners). We wanted the very first run to be a complete non‑event. A few practices got us there:

Dry‑run first. Evergreen ships with a DRY_RUN mode that logs every write it would make without touching a single collaborator or repo. We ran it against the real org and read the logs like tea leaves until we trusted the decisions it wanted to make.

Overcommunicate. Before flipping the switch, we broadcast what was coming, when, and what people needed to do, so the first issue anyone saw wasn’t a surprise. We found that when you’re telling a large group the same thing for the seventh time, it’s often when many are still hearing it for the first time.

Watch everything with Splunk. Evergreen emits structured logfmt logs to a dedicated Splunk index. That observability is how we caught edge cases in the wild (empty collaborator lists, unusual permissions, repos with issues disabled) and tightened the logic before they mattered.

Respect the platform’s speed limits. When you open issues and post comments across every repo in a big org, you slam into GitHub’s secondary rate limits for content creation: 80 requests/minute and 500/hour. While this is a thoughtful preventative control to avoid system abuse, it requires a bit of intention when automating IssueOps at large scale.

So Evergreen paces itself by construction. It processes repos in batches, spaces out each content‑creating call by a couple of seconds, and sleeps between batches to let the rolling window clear, and it only counts the repos that actually create content, so a quiet quarter where nothing’s eligible still runs fast. We opted for proactive avoidance over reactive back‑off.

Lessons we’re taking with us

  • Make the safe path the default path. Fail secure, then make responding easy enough that failing secure rarely triggers.
  • Use the primitives you already have. Issues, webhooks, custom properties, and git history did the work of a bespoke UI, a job queue, and an audit database.
  • Meet people where they work. An issue in your repo beats a dashboard you’ll never open.
  • Logs are a revert button. Writing every change into the issue turned “oops” into “paste these three handles into a Copilot session.”
  • Respect the limits. At org scale, rate limits aren’t an edge case: they’re the design constraint.

Keep your org evergreen

Routine hygiene is the kind of work that’s easy to defer and perfect to automate. The trick isn’t heroic cleanup sprints: it’s making the boring, safe thing happen on a schedule, with a friendly face and an undo button.

That’s Evergreen. And because it’s built entirely from native GitHub features, you can stand up the same pattern yourself.

Ready to make repository hygiene routine? Start with one recurring access or archival task, then use GitHub Apps, actions, issues, and custom properties to automate the problem away.

What happened?

Impact summary

Duration: approximately 2 hours

Customers may have seen requests fail, run slowly, or remain pending when opening or updating issues and pull requests, calling APIs, creating access tokens, starting GitHub Actions workflows, or signing up.

~96% of the customer requests creating issues through the web interface were impacted during the incident window. In addition, 90% of new customer signup and ~4% of actions workflows also experienced intermittent failures.

What went wrong and why?

A background data-cleanup job increased load on a shared database. The job had a safeguard designed to slow its writes when database replicas fell behind, but the safeguard did not account for incoming load on the primary database server. As a result, the job continued running until the primary reached its connections limit. When the primary ran out of available connections, requests that depended on it could not complete reliably.

Two other factors increased the impact and delayed recovery. First, there was no quick timeout on these database calls, so request handlers waited on the stalled database instead of failing fast. Second, a retry loop around token creation kept resending writes that were already failing, which held the database saturated rather than letting it recover.

How did we respond?

  1. A background data-cleanup job began writing to a shared database.
  2. The job’s safeguard monitored replica lag but did not account for load building on the database’s primary server.
  3. The primary ran out of available connections, causing requests across dependent services to fail or run slowly.
  4. Automated monitoring detected the incident, and we traced the failures to load on the shared database.
  5. We reduced internal load and paused the background job.
  6. The database recovered, and error rates across the affected services returned to normal.

How are we making incidents like this less likely or less impactful?

  • We are implementing additional safeguards to improve database resilience and service availability. These measures will better control background processing based on available database capacity, reduce unnecessary retries during failures, and limit the impact of slow database requests.
  • We are also improving service startup behavior to ensure that temporary database connectivity issues do not unnecessarily affect service recovery.

Maintainers look at star history to answer a practical question: did a launch, release, or event change a project’s trajectory? To reconstruct that curve from the GitHub API, tools had to request pages of stargazer records (each person who currently stars the repository and when they starred it), keep the timestamps, and throw the identities away.

Over time, that design created problems at both ends. Identities were available for bulk collection, so bad actors started scraping public stargazer lists for spam and phishing campaigns. For highly starred repositories, the endpoint could also make the database process many thousands of entries to return a single page.

The fix seemed clear: return counts instead of people. But returning less data didn’t actually make the query any cheaper.

Now maintainers have a direct way to get the curve: we built an endpoint that returns up to 30 weeks of daily star counts in a single request, with no identities attached. Keeping that cheap to serve meant reducing how much data the database processed, not just how much it returned, and the endpoint does that by filtering stars by time before it counts anything.

What maintainers need from star history

We first addressed the immediate risks to developers and to our database by restricting stargazer and watcher lists to repository administrators and collaborators. After the access change, callers without the required permission could receive an empty response or a 403 Forbidden response.

That change also cut off tools that had used the old response to calculate star history, often without displaying or otherwise using the usernames it returned. So we talked with maintainers and tool builders to understand what they still needed. They used star history as an approximate signal of interest: to compare activity before and after a release, or to see whether an announcement reached new developers. What they cared about was the curve.

The old API response had made identity look like part of that contract because every timestamp arrived attached to a user. In practice, tools such as Star History needed counts and dates, not usernames or other user data. Once identity was no longer part of the requirement, we could design an aggregate endpoint for the actual job: retrieving changes in star counts over time at a useful resolution.

When the API change disrupted Star History, users rallied around the project. GitHub’s Community team listened and connected us with product engineering, who dug into our use case and worked alongside us to design a purpose-built endpoint. A difficult situation became a constructive collaboration between GitHub, Star History, and the broader community—ultimately leading to a better solution.

Tianzhou Chen, star-history.com maintainer and Bytebase co-founder

Why the original endpoint was expensive

Once we knew what maintainers needed, the next step was understanding why the original design couldn’t provide it cheaply. The original GET /repos/{owner}/{repo}/stargazers endpoint was built to answer a simple question: who starred this repository? It returned a paginated list of people, and if the request specified a custom media type, each entry also included when the star was created.

The star model was built for the same job. It records the current set of people who have starred a repository, which keeps showing a star count or a list of stargazers simple. It was not designed as a historical event log: when someone removes a star, that record is removed. When tools began using the list as a time series, reconstructing a growth curve meant retrieving individual identities and processing every current star. Because each page held at most 100 people, the work grew with the repository’s popularity: building the full curve for react/react, with about 251,000 stars, took about 2,511 requests, so tools often ran into rate limits or sampled pages instead of reading them all.

Serving a page required the database to query the repository’s current stars. Due to a bug in the pagination implementation, every request also counted all of those stars to work out how many pages existed, even though the caller received only one page of up to 100 people. On a highly starred repository, that meant counting many thousands of entries on every request. In the week before we restricted access, nearly 37,000 of these count queries ran slowly enough to be logged, averaging nearly 3 seconds each, and database safeguards killed more than 1,000 of them, which contributed to request timeouts.

The chart below shows what all that counting cost. After we restricted access, the database served about 60% fewer stargazer requests, and the total time it spent on the count query fell by about 80%.

Approaches we considered

Removing identities handled the privacy requirement. The harder part was keeping each request from scanning the repository’s entire current star set.

Keeping events without identities

Our first spike kept one record per star and returned the starred_at value without the stargazer’s identity for callers who lacked collaborator access. At first, this looked like the quickest path forward, because it directly served the request we had heard from tool builders. It also closed the identity-harvesting path with a relatively small change to the existing serialization and authorization flow.

This approach addressed identity exposure and would have allowed existing tools to keep working. But API consumers would still have to paginate through and process potentially many thousands of individual records to build an aggregate history. It also tied the new use case to an endpoint and pagination model designed for listing people rather than retrieving trends.

Aggregating, then paginating

Aggregation seemed like the obvious next step. Instead of returning one row per star, the query could group stars into daily or weekly buckets, sort those buckets, and paginate the much smaller result.

The problem was where pagination happened. In a straightforward SQL query, the database first finds all stars for the repository, groups them into buckets, and sorts those buckets. Only then does it apply LIMIT, which controls how many buckets are returned, and OFFSET, which determines where the page begins:

all matching stars -> bucket every row by day or week -> sort every bucket -> OFFSET/LIMIT -> response

For a popular repository, an anonymous request could still scan and aggregate many thousands of index entries to return a handful of buckets. Returning fewer buckets would shrink the JSON response, but it would not reduce the expensive grouping and sorting the database had already performed. For react/react, reading the full history that way would have meant examining roughly 6 million rows, because every one of the 24 requests would have reprocessed all of its stars. To reduce the query cost, we had to narrow the rows before aggregation began.

Filtering by time before grouping

The design we shipped paginates star history by calendar week. For each request, it translates page and per_page into an indexed created_at range, filters the stars to those weeks, and then groups the matching records into daily counts. A response includes up to 30 weeks, and increasing page moves backward through the repository’s history.

indexed date range -> group rows in that range -> daily buckets -> response

With the date range applied first, each request processes the weeks being returned instead of every current star in the repository. For tools, that means one request now covers up to 30 weeks of history, no matter how many stars the repository has. For react/react, that’s about 24 requests instead of about 2,511, and the database examines each star about once (roughly 251,000 rows) across the full history. This fits the primary use case because maintainers usually inspect growth across weeks or around a known release, launch, or event. Week-based ranges also align with other repository activity APIs: the response follows the same shape as the weekly commit activity endpoint, GET /repos/{owner}/{repo}/stats/commit_activity.

The time-range design limits each request to a defined period, but it does not limit the number of stars within that range. A week with an unusually large number of stars can therefore still produce a slow or expensive query. The normal request path no longer queries every current star, but exceptionally dense weeks remain a scaling limitation.

Comparing the performance of the old and new API paths also surfaced other places where GitHub was counting stars on demand. We found the same pattern on the repository stargazers page on GitHub.com and updated it to use the repository’s cached star count. Slow queries from that page, which had numbered in the hundreds each week, dropped to zero. We recently shipped a similar fix to other stargazer API endpoints.

What we learned

  1. A smaller response does not always mean a cheaper query. LIMIT and OFFSET reduced the number of results returned, but they did not reduce the grouping and sorting the database had already done. We had to look at the order in which the work happened.
  2. Start with what people are actually trying to do. Maintainers needed to compare trends. A list of identities was simply how the old endpoint happened to provide the underlying data.
  3. Return only what the use case needs. Anything more is data someone else can misuse. Once we understood the job, we could remove individual identities without taking away the information maintainers relied on.
  4. Be clear about the tradeoffs that remain. The new endpoint is safer and more predictable, but calendar boundaries, removed stars, and unusually dense weeks still affect what it can return. Those details are part of the API contract too.

Restricting the original endpoint addressed the immediate problem. Listening to maintainers gave us something better than what we started with: star history that’s easier to get, cheaper to serve, and safer for everyone who stars a project.
